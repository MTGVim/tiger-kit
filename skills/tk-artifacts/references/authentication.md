# worktree 내부 애플리케이션 인증

승인된 비운영 애플리케이션 인증에서는 같은 작업과 worktree, 애플리케이션, 검증된 로그인 출처, 환경 및 계정과 역할 안에서 보호된 입력 파일을 재사용합니다. 관련 스킬이 계속 작업할 수 있도록 비밀이 아닌 경로와 대상 연결 정보를 보존합니다. 다른 worktree나 Git 공통 디렉터리에서 인증 정보를 찾지 않습니다. access/session 자료, 선택적인 refresh token과 명시적으로 승인된 개발/QA 비밀번호는 사용자가 삭제를 요청하거나 승인된 worktree 정리가 이루어질 때까지 유지합니다. 실제 대상 환경과 인증 정보의 용도를 확인합니다. 운영 애플리케이션의 개발/QA 환경도 해당할 수 있지만, 계정명이나 파일명만으로 비운영 범위임이 입증되지는 않습니다. 단계 완료, 중단, 검증 실패, access-token 만료와 일반적인 자원 정리는 이 파일을 삭제하는 사유가 아닙니다. 이 예외에는 실제 운영 인증 정보, OTP와 복구 코드가 포함되지 않습니다. 명시적으로 승인된 개발/QA 범위 밖의 비밀번호는 계속 임시 입력 정리 규칙을 따릅니다. 보존은 새로운 로그인, 주입이나 갱신 권한을 부여하지 않습니다. 자식이 부모의 입력을 재사용할 때는 부모가 정한 파일 소유자와 수명 주기를 유지합니다. 소유권, 수명 주기나 대상 연결 정보가 없거나 충돌하면 부모가 경계를 해결할 때까지 입력을 소비하거나 덮어쓰거나 삭제하지 않습니다. 인증 파일을 근거, Git, 인수인계나 전역 캐시에 포함하지 않습니다.

사용하기 전에 안전한 경로, 소유권, 제외 상태와 비밀 권한을 다시 확인하고, 현재 스냅샷과 인증된 대상 상태를 비공개로 검증합니다. 만료는 사용 제한이며 파일 삭제 조건이 아닙니다. 만료되거나 거부된 것으로 알려진 access 자료를 주입하거나 수명을 모르는 자료를 유효하다고 취급하지 않습니다. 수명을 지어내지 말고 애플리케이션이 지원하는 세션/만료 확인을 통해 준비 상태를 판정합니다. 대체 입력을 요청하기 전에 기존의 안전한 세션 상태와 저장소 또는 애플리케이션이 지원하는 갱신 경로를 조사합니다. 검증된 endpoint, client 인증, cookie/header/body와 응답 계약을 사용합니다. refresh token만으로는 충분하지 않습니다. 인증 정보가 담긴 redirect나 로그 없이, 지원되는 신뢰할 수 있는 전송 경로를 통해 동일하게 승인된 신원과 범위만 갱신합니다.

작업에는 갱신 담당자를 하나만 둡니다. 부모와 자식 소비자는 그 담당자를 통해 갱신을 직렬화하고 갱신 후 다시 읽습니다. 프로젝트에 기존 client 조정 기능이 있으면 재사용합니다. 프로세스 간 잠금을 제공한다고 주장하거나 전역 token 관리자를 만들지 않습니다. 갱신 결과를 비공개로 검증하고 회전된 refresh token을 포함하여 같은 보호 파일을 원자적으로 갱신하되 사용자가 동시에 편집한 내용을 덮어쓰지 않습니다. refresh 필드가 없을 때는 애플리케이션 계약이 허용하는 경우에만 이전 값을 보존합니다. 회전형 refresh 요청의 결과가 불분명하면 재사용 전에 지원되는 세션 상태를 대조해 확인합니다. 이전 refresh token으로 무작정 재시도하거나 다른 소비자와 경합하지 않습니다.

지원되는 자율 복구가 없거나 새로운 로그인이 필요하다는 사실이 입증된 경우에만 필요한 최소한의 사용자 입력을 요청합니다. 예를 들면 갱신 자료가 없거나 refresh 권한이 철회되었거나 만료된 경우입니다. 네트워크/HTTP 실패만으로 인증 정보가 무효라는 사실이 입증되지는 않습니다. 파일을 보존하고 실패를 진단하며, 진행할 수 없다면 해당 단계를 차단되었거나 검증할 수 없는 상태로 보고합니다. 재개 전에 인증이 복구되었는지 독립적으로 확인합니다. 이는 현재 작업의 절차이며 백그라운드 갱신이나 세션 종료 후 호스트의 재개를 보장하지 않습니다.
