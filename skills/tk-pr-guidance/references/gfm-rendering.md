# PR 본문·댓글의 GFM 사전 확인

PR을 생성하거나 기존 본문·선택된 댓글을 갱신하기 직전에 읽습니다. 미디어 섹션 삽입과
스택 각 계층의 본문에도 적용합니다. 실제 쓰기 권한은 호출자가 유지합니다. 이 확인은 새로운
PR·댓글, 업로드, 인증 설정이나 외부 서비스 사용 권한을 부여하지 않습니다.

## 정확한 후보를 렌더링한다

1. 현재 대상의 원시 Markdown과 적용되는 템플릿을 읽고, 승인된 변경만 반영한 최종 UTF-8
   후보를 준비합니다. 제목·섹션 순서·HTML 주석·체크리스트와 무관한 본문 바이트를 보존합니다.
   의도한 취소선과 코드로 표시할 리터럴을 해당 후보에서 식별합니다.
2. 지원되는 GitHub 경로로 [Markdown API](https://docs.github.com/en/rest/markdown/markdown)의
   `POST /markdown`을 호출합니다. `text`에는 후보 파일에서 읽은 정확한 본문,
   `mode`에는 `gfm`, `context`에는 실제 `<owner>/<repo>`를 넣습니다. `markdown` 모드나
   `/markdown/raw`로 대체하지 않습니다. 이미 지원되는 `gh`를 쓴다면 요청 JSON 파일을
   만든 뒤 `gh api --method POST markdown --input <request.json>`으로 HTML을 받습니다.
   본문을 shell 문자열에 끼워 넣거나 백틱·달러·줄바꿈이 재해석되는 방식으로 전달하지 않습니다.
3. 응답 HTML의 요소와 표시 텍스트를 확인합니다. 의도하지 않은 `<del>`이 없어야 합니다.
   의도한 취소선은 유지하고, 코드로 표시할 각 리터럴은 HTML entity를 해석한 하나의 `<code>`
   요소 안에 온전히 있어야 합니다. 태그처럼 보이는 코드 문자열을 실제 요소로 세지 않습니다.
   코드가 중간에 끝나거나 일부가 본문으로 빠져나온 경우는 실패입니다. 표·체크리스트·링크도
   의도한 구조인지 확인하며, 렌더링 HTML을 원래 Markdown 대신 발행하지 않습니다.
4. 정확한 후보의 식별 정보, 저장소 context와 실제 검사 결과를 호출자의 기존 실행 근거에
   결합합니다. 후보를 수정했거나 원격 본문과 병합해 바이트가 달라지면 다시 렌더링합니다.
   검사한 후보와 실제 쓰기 입력이 같은지 확인한 뒤 쓰고, 완료 전에 원격 Markdown을 다시 읽어
   승인된 변경과 대조합니다. 이 기록을 위해 별도 지속 원장을 만들지 않습니다.

GitHub 렌더링이 실패하거나 필요한 경로·권한을 사용할 수 없으면 해당 본문 쓰기를
`Blocked | Unverifiable`로 보류합니다. 로컬 파서·정규식 검사는 사전 진단으로 사용할 수 있지만
GitHub GFM 확인을 통과했다고 보고하지 않습니다. 자동 설치·로그인·설정 변경으로 우회하지 않습니다.
브라우저에서 PR 페이지를 여는 시각 확인은 별도이며, 이 API 확인이 브라우저·미디어 재생 검사는 아닙니다.

## 범위와 백틱 리터럴을 보존한다

- 코드 밖에서 범위를 나타내는 `~`는 `\~`로 씁니다. 예를 들어 `a\~b 및 c\~d`는 두 범위를
  그대로 보여 줍니다. 코드·링크 URL·HTML 주석·템플릿 전체를 무차별 이스케이프하지 않습니다.
  의도한 취소선은 범위 표기와 구분해 유지합니다.
- 백틱이 들어 있는 리터럴은 내용에서 가장 긴 연속 백틱보다 긴 동일한 길이의 백틱 구분자로
  감쌉니다. 내용에 백틱 하나만 있으면 구분자 두 개로 ``a`b`` 같은 리터럴을 표시합니다.
  내용이 백틱으로 시작하거나 끝나면 구분자와 내용 사이에 양쪽 공백 하나를 넣고 실제 `<code>`
  텍스트를 대조합니다. 코드 스팬 안에서 백슬래시로 백틱을 이스케이프하지 않습니다.
  정확한 줄바꿈·앞뒤 공백이 필요한 내용은 적합한 코드 블록을 사용하고 원본과 비교합니다.

다음은 문법을 설명하는 Markdown 소스입니다.

````text
범위: a\~b 및 c\~d
리터럴: ``a`b``
시작과 끝에 백틱이 있는 리터럴: `` `a` ``
````

## 미디어 업로드와 본문 변경이 결합된 경로

선택한 도구가 업로드와 본문 변경을 함께 수행하면서 미디어 토큰을 재작성하면, 실행 전에는
실제 작성한 본문 파일을 위 절차로 검사합니다. 검토한 현재 도구 계약이 허용하는 미디어 토큰·URL
치환만 미확정으로 남기고 정확한 위치와 한계를 기록합니다. 실행 뒤에는 원격의 최종 Markdown을
다시 렌더링하여 검사하고, 도구가 해당 토큰 이외의 본문을 바꾸지 않았는지 대조합니다.
사후 검사를 최종 원격 바이트에 대한 사전 검증이라고 보고하지 않습니다.

미리보기에서 정확한 최종 본문을 얻을 수 있는 경로는 그 바이트를 쓰기 전에 검사합니다. 토큰 재작성
범위를 확인할 수 없거나 작성한 본문의 사전 검사가 실패하면 결합 명령도 실행하지 않습니다.
실행 뒤 예상 밖 본문 변경이나 GFM 실패가 있으면 후속 발행·완료를 중단하고 실제 원격 상태를
보고합니다. 이미 승인된 범위 안에서 안전하게 교정할 수 있는 변경만 처리하고, 교정 후보도 다시
검사합니다. 새 업로드·추가 댓글이나 알리지 않은 경로 전환으로 복구하지 않습니다.

## 출처와 적용 범위

2026-11-02에 GitHub 공식 Markdown API와 [GFM 0.29](https://github.github.com/gfm/)의
6.1·6.3·6.5를 확인했습니다. 고정한 [`github/cmark-gfm@27d942c8b0a62d192f616e5bf3578f4b6a89e180`](https://github.com/github/cmark-gfm/tree/27d942c8b0a62d192f616e5bf3578f4b6a89e180)의
`extensions/strikethrough.c`, `test/extensions.txt`도 대조했습니다.
**keep:** 저장소 context를 적용한 GFM 해석과 코드 스팬·취소선 의미를 유지합니다.
**adapt:** 원격 쓰기 전에 정확한 후보를 확인하고 결합 첨부의 서버 치환만 별도로 검증합니다.
**omit:** 새 외부 렌더러·도구 의존성·상시 테스트 모음과 브라우저 확인의 의무화는 도입하지 않습니다.
이 출처 확인은 모든 GitHub 후처리·브라우저 표시·미디어 플레이어의 실행 검증이 아닙니다.
