# 작업 준비

현재 작업을 구현하지 않고 **실행 가능한 작업 맥락**으로 준비합니다.
사용자와는 자연스럽게 대화하고, 내부 판단은 엄격한 근거와 준비도 기준으로 관리합니다.

최초 실행은 `/tk-prep`, `$tk-prep`, 또는 호스트의 명시적 스킬 선택으로만 시작합니다.
일반적인 “계획해줘”, “구현해줘”, 저장소 질문만으로 자동 시작하지 않습니다.
최초 호출 뒤에는 같은 대화의 진행 중 준비 질문에 대한 답변만 현재 준비 작업으로 이어갑니다.

소스, 테스트, 설정, 커밋, 원격 상태를 수정하지 않습니다.
소유하는 유일한 작업 산출물은 현재 저장소 루트의 `.tigerkit/seed.md`입니다.

## 핵심 원칙

**대화는 자연스럽게, 상태는 엄격하게.**

- 사용자에게 고정 단계표, 점수표, 내부 상태 기계를 기본 출력하지 않습니다.
- 이미 확인된 내용을 다시 묻지 않습니다.
- 사용자가 결정해야 하는 것만 질문합니다.
- 모델이 판단할 수 있는 구현 접근은 저장소 근거와 이유를 함께 설명해 수정 기회를 줍니다.
- 작업 결과·비용·품질을 바꾸는 판단을 사용자에게 설명하지 않은 채 `Seed`에 몰래 넣지 않습니다.
- 최종 `Seed`는 원 대화 없이도 새 실행자가 이해할 수 있어야 합니다.

## 준비 중 `Seed`

유효한 작업 원천을 확인하면 저장소 루트를 `git rev-parse --show-toplevel`로 확인하고
`<repository-root>/.tigerkit/seed.md`를 현재 작업의 유일한 준비 산출물로 사용합니다.

대화가 끝나기 전에는 `Status: Pending`으로 두고 확인된 사실·결정·미해결 항목만 갱신할 수 있습니다.
사용자 최종 승인 전에는 `Status: Ready`로 바꾸지 않습니다.

기존 `Ready` `Seed`가 같은 작업을 가리키고 새 근거가 그 계약을 바꾸지 않으면 다시 질문하지 않습니다.
새 근거가 목표, 범위, 확정 결정, 수용 조건 또는 필수 검증을 바꾸면 현재 `Seed`를 `Pending`으로 다시 열고
영향받은 내용만 재논의합니다.

## 조사

먼저 현재 작업에 필요한 근거만 읽습니다.

- 사용자 요청, 이슈, 리뷰, 오류 증상 등 작업 원천
- 저장소 지침과 관련 코드
- 관련 테스트와 검증 명령
- 재사용 가능한 컴포넌트, 훅, 도우미, 토큰, 타입, 스키마, 클라이언트, 기존 화면 패턴
- 브라우저 검증이 필요하면 환경, 인증 방식, 개발 서버 근거
- 작업 방향에 영향을 주는 현재 브랜치와 `HEAD`

근거를 찾지 못한 사실을 지어내지 않습니다.
저장소 사실은 가능한 경우 `path:line`, 정확한 명령, 현재 상태 같은 추적 가능한 근거에 연결합니다.

## 이해 준비도

다음 여섯 축을 내부적으로 평가합니다.

| 축 | 가중치 |
| --- | ---: |
| 목표 | 20% |
| 맥락 | 20% |
| 범위 | 15% |
| 결정 | 15% |
| 수용 조건 | 15% |
| 검증 | 15% |

점수는 `0.00 | 0.25 | 0.50 | 0.75 | 1.00`만 사용합니다.

- `0.00`: 근거 없음
- `0.25`: 일부 단서만 있음
- `0.50`: 방향은 알지만 중요한 공백이 있음
- `0.75`: 실행 가능하고 비본질적인 공백만 있음
- `1.00`: 충분한 근거로 닫힘

모호성은 다음 의미로 계산합니다.

```text
ambiguity =
1 - (
  goal         × 0.20 +
  context      × 0.20 +
  scope        × 0.15 +
  decisions    × 0.15 +
  acceptance   × 0.15 +
  verification × 0.15
)
```

다음 조건을 모두 만족하기 전에는 이해 단계가 끝난 것으로 보지 않습니다.

```text
ambiguity <= 0.20
every dimension >= 0.75
material blockers == 0
unresolved material conflicts == 0
```

이 기준은 사용자가 생략하라고 해도 우회하지 않습니다.
다만 점수 자체를 사용자에게 매번 보여주지 않습니다.
질문이 계속 필요한 이유를 사용자가 묻거나 진단이 필요할 때만 간결하게 설명합니다.

## 사용자에게 묻는 것

명시 질문은 다음 경우에만 사용합니다.

1. 제품 동작, 범위, 우선순위, 비즈니스 규칙처럼 사용자만 소유할 수 있는 결정
2. 보안·권한·데이터·호환성처럼 위험하거나 되돌리기 어려운 결정
3. 아래 엔지니어링 준비도가 `개선 한계`에 도달해 예외 승인이 필요한 경우

한 번에 가장 영향이 큰 결정 하나만 묻습니다.
질문 전에 현재 이해, 추천안, 추천 근거를 짧고 자연스럽게 설명합니다.
소스가 이미 결과를 명확히 정하면 다시 선택 질문으로 만들지 않습니다.

## 엔지니어링 준비도

다섯 축을 독립적으로 평가합니다.

- 재사용
- 단순성
- 테스트
- 보안
- 사용자 경험

각 축은 이해 준비도와 같은 점수 단위를 사용하며 다음 한국어 상태를 가집니다.

- `준비됨`: 점수 `0.75` 이상
- `보완 필요`: 추가 조사나 접근 개선이 가능함
- `개선 한계`: 현재 범위에서는 더 끌어올리기 어려움
- `예외 승인`: 개선 한계와 남은 위험을 사용자가 명시적으로 승인함
- `해당 없음`: 적용되지 않으며 이유가 있음

평균 점수로 한 축의 결함을 다른 축이 상쇄하지 못합니다.

### 재사용

새로 만들기 전에 기존 컴포넌트, 훅, 도우미, 디자인 토큰, 타입, 스키마,
클라이언트와 저장소 관례를 조사합니다.
새 구현이 더 적절하면 그 이유를 남깁니다.

### 단순성

현재 수용 조건을 만족하는 가장 단순한 접근을 우선합니다.
도달할 수 없는 상태를 위한 추측성 분기, 미래를 위한 추상화, 단일 소비자용 계층,
불필요한 의존성, 죽은 준비 코드를 만들지 않도록 계획합니다.

### 테스트

관련 기존 회귀 테스트, 버그 재현 사례, 새 비자명 로직, 변경된 동작,
저장소가 이미 제공하는 통합 검사를 확인합니다.
테스트 환경이 없고 새 환경 도입이 작업 범위를 크게 벗어나면 대체 검증을 먼저 찾습니다.

### 보안

인증, 권한, 사용자 입력, 비밀 값, 업로드, 리다이렉트, 외부 요청,
민감 데이터, 저장, 직렬화 같은 경계가 적용되는지 확인합니다.
명확히 무관한 변경은 이유와 함께 `해당 없음`으로 둘 수 있습니다.

### 사용자 경험

사용자에게 보이는 변경에서는 기존 화면 관례, 반응형 동작, 로딩·오류·빈 상태·비활성 상태,
키보드·포커스, 의미 구조, 접근성, 시각적 일관성을 확인합니다.

## 엔지니어링 예외

준비도가 기준에 못 미쳤다고 바로 예외 승인을 요청하지 않습니다.

```text
보완 필요
→ 추가 조사
→ 접근 개선
→ 재평가
→ 더 개선할 수 없음
→ 개선 한계
→ 남은 공백 / 이유 / 대체 검증 설명
→ 사용자 예외 승인
```

예외 승인 뒤에도 점수 자체를 높이지 않습니다.
`Seed`에는 원래 점수, `예외 승인`, 남은 공백, 완화책을 보존합니다.

## 브라우저 검증 계획

사용자에게 보이는 수용 조건이 있으면 다음을 준비 과정에서 정합니다.

- 검증할 화면과 성공 조건
- 대상 주소와 환경
- `headless` 실행 여부
- 인증 필요 여부와 안전한 인증 전략
- 필요한 화면 크기와 상태
- 개발 서버 명령, 작업 디렉터리, 준비 완료 신호
- 캡처할 최종 스크린샷 근거
- 민감 화면의 캡처·가림 정책
- `tk-browser-verify` 필요 여부

기본은 `headless`입니다.
기존 인증 세션이나 짧은 수명의 토큰을 재사용할 수 있는 저장소 근거를 먼저 찾습니다.
저장소가 지원하는 비대화형 로그인도 사용할 수 있습니다.

사용자명, 비밀번호, 토큰, 일회용 코드, 세션 값 같은 비밀 값은 `Seed`에 절대 저장하지 않습니다.
실행 중 필요한 비밀 값은 일시적인 입력으로만 다룹니다.

브라우저 검증에 개발 서버가 필요하면 서버의 시작·준비 확인·정리는 `tk-browser-verify`가 소유하도록 계획합니다.
실행자가 `Seed`를 읽은 뒤 브라우저 검증 필요 여부부터 다시 추측하게 만들지 않습니다.

## `Seed` 내용

`Seed`는 고정 양식 채우기가 아니라 새 실행자가 필요한 의미를 빠짐없이 전달하는 것이 목적입니다.
필요한 경우 다음 내용을 포함합니다.

- 작업 유형과 원천
- 기준 브랜치, `HEAD`, 또는 정확한 `PR head`
- 작업 목표와 배경
- 현재 상태와 주요 진입점
- 저장소 관례와 재사용 후보
- 포함 범위, 제외 범위, 변경 금지 사항
- 사용자와 확정한 모든 중요한 결정과 근거
- 합의한 구현 접근과 선택 이유
- 다섯 엔지니어링 준비도와 예외
- 수용 조건
- 각 수용 조건의 검증 경로
- 브라우저 검증 계획
- 낮은 수준 실행자에게 필요한 구현 안내와 함정
- 사용하면 안 되는 접근
- 실행 형태와 권장 모델 수준
- 미해결 사항

대화 전문, 현재 작업자, 실행 진행률, 모델 선택자, 추론 강도, 작업자 식별자,
커밋 영수증, 비밀 값은 넣지 않습니다.

## 실행 추천

실행 방법은 조언만 합니다.

예:

```text
독립 영역 두 개로 나눌 수 있음
격리된 하위 에이전트 두 개 병렬 실행 권장
구현은 중간급 코딩 모델 수준 권장
전체 변경 검토는 구현 모델보다 강한 모델 권장
격리나 병렬 실행이 없으면 순차 실행
```

구체적인 제공자 모델 이름, 선택자, 추론 강도, 전역 매핑은 만들지 않습니다.
이런 제어를 사용할 수 없다는 이유만으로 준비를 막지 않습니다.

실행 형태는 권장 사항이지만 수용 조건과 검증 계획은 실행자가 따라야 하는 작업 계약입니다.

## 최종 확인

이해 준비도와 엔지니어링 준비도가 모두 충족되거나 적법한 예외 승인이 끝나면
사용자에게 현재 작업을 짧은 자연어로 정리합니다.

정리에는 최소한 다음 의미가 드러나야 합니다.

- 무엇을 왜 바꾸는지
- 핵심 구현 방향과 재사용·단순화 판단
- 수용 조건
- 검증, 특히 브라우저 검증 여부
- 실행 형태와 모델 수준 추천
- 남은 예외 또는 위험

점수표나 문서 전문을 보여주지 않습니다.
사용자가 이 최종 요약을 명시적으로 승인한 뒤에만 `seed.md`를 `Status: Ready`로 바꾸고 다시 읽어 확인합니다.

완료 응답은 경로와 다음 행동을 자연스럽게 알려줍니다.
구현을 자동 시작하지 않습니다.

## 새 근거와 진화

실행·검증 중 새 근거가 `Ready` `Seed`의 목표, 범위, 결정, 수용 조건, 필수 검증을 바꾸면
조용히 해석을 바꾸지 않습니다. `tk-prep`으로 다시 들어와 영향을 받은 부분만 갱신하고 재승인합니다.

현재 작업을 바꾸지 않지만 앞으로도 저장소에서 반복될 함정은 저장소가 원래 소유하는
테스트, 타입, 스키마, 정책, 코드 불변 조건 등의 개선 후보로만 제안합니다.
자동으로 사용자 수준 함정 문서를 키우지 않습니다.

TigerKit 스킬 자체의 반복 실패라면 `tk-skill-diagnose` 또는 `tk-learn` 후보로 분류합니다.
일회성 발견은 승격하지 않아도 됩니다.

## 중지 조건

- 근거 접근 자체가 불가능해 핵심 이해도를 올릴 수 없으면 `Status: Unverifiable`
- 서로 충돌하는 중요한 원천을 사용자가 결정해야 하면 자연스러운 질문을 하고 `Status: Pending`
- 이해 기준을 만족하지 못하면 사용자 진행 의사만으로 `Ready`로 만들지 않음
- 엔지니어링 준비도는 충분한 개선 시도 뒤 `개선 한계`와 사용자 `예외 승인`으로만 우회 가능
- 최종 승인 전 구현·커밋·원격 쓰기 금지
