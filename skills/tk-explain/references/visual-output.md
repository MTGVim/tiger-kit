## 삽화 배치·밀도와 시각적 일관성

설명 페이지 또는 다중 섹션 문서에 그림을 실제로 제작할 때만 [삽화 기획](illustration-planning.md)을 읽습니다. 설명의 핵심 주장과 원문은 먼저 고정하고, 그림이 추가적인 이해를 주는 영역만 고릅니다. 이 판단은 특정 모델·이미지 개수·여러 장 제작을 강제하지 않습니다. 기본 페이지의 일러스트레이션 한 장 원칙은 유지하고, 명시된 긴 문서의 삽화 추가 또는 사용자에게 위임된 다중 섹션 시각 자료에서만 독립적인 보조 삽화를 고려합니다. 일반 대화·짧은 설명·정확한 수치 도해·만화·영상에는 별도 이미지 생성 계획을 강제하지 않습니다.


# 시각 출력 선택

산출물을 요청했거나, 결과물에 불만족을 표하거나 다른 방식을 요청했거나, 전체 기법 목록을 보고 싶다고 했을 때 [설명 선택](explanation-selection.md)을 읽습니다. 일반 대화에서는 필요한 경우 [설명 기법](../../tk-writing/references/explanation-techniques.md)의 글로 적용할 수 있는 원리를 사용하며 전체 메뉴나 형식 질문을 강제하지 않습니다. 직접 조작·움직임·그림이 필요한 기법을 글로만 대신하고 구현했다고 주장하지 않습니다.
요청된 HTML에서는 기법이나 구성을 고르기 전에 [렌더러 계약](../../tk-writing/references/renderer-contract.md)의 내용 형태별 분기와 제작 전 형식 제안을 적용합니다. 이미 선택했거나 위임한 형식은 다시 묻지 않습니다. 그 외 산출물의 기법이 미지정이면 근거, 주제, 독자와 요청 형식에 맞는 기법 하나를 골라 제작합니다. 불만족이나 다른 방식 요청에는 서로 다른 후보 세 개를 이유와 한계와 함께 제시하고 선택을 받습니다. 전체 카탈로그는 사용자가 전체 목록을 요청할 때만 보여 줍니다. 기법, 호환 형식, 그리고 관련된 경우에만 이미지 스타일과 종횡비를 확정합니다. 이미 지정된 축은 건너뛰고 내부 다이어그램 세부 유형은 묻지 않습니다. 정확한 ID와 적합성 규칙은 설명 선택 참조가 소유합니다.
대화 설명 뒤에 `HTML로` 같은 후속 요청을 받으면 유효한 기존 근거를 재사용해 같은 추천 제작 흐름을 따릅니다. 이 경우에도 3단계의 렌더러·작성자·정적 검사와 4단계의 해당 정확성 확인을 생략하지 않습니다. 근거가 낡았거나 범위가 바뀌었으면 먼저 보완합니다.
보통 설명 하나를 만듭니다. 명시적인 기법 비교는 최대 다섯 변형을 허용하고 명시적인 폭넓은 탐색은 최대 열다섯 변형을 허용합니다. 대상 비교만으로 변형을 요청한 것은 아닙니다.
증류된 네 가지 원칙은 다른 평가 관문 뒤에 두지 말고 이용 가능한 선택 집합에 유지합니다.
공통 근거를 사용하는 변형 검사, 블라인드 비교 인계와 동의 기반 외부 선호 사용은 해당 참조가 소유합니다. 기법 선택은 비교 동의나 메모리 쓰기 동의를 부여하지 않습니다.

레이아웃을 잡기 전에 명시된 목적지에 맞춰 전달물을 선택합니다. PR 본문이나 이슈를 위한 정밀 인포그래픽 또는 요약 시각 자료는 별도의 형식 질문 없이 간결한 PNG 하나를 기본으로 합니다. [요약 이미지](summary-image.md)를 읽습니다. 그 목적지에서는 요청한 경우에만 설명 페이지를 만듭니다. 명시적인 페이지·HTML 요청은 PR 목적지에서도 페이지 경로를 유지합니다.
기술 스택을 로고·역할·그룹으로 보여 주는 `S 기술 스택 맵`을 선택하면 [기술 스택 맵](stack-map.md)을 읽습니다. 기본 전달물은 정밀 PNG 하나이며, 설명 페이지는 명시적으로 요청한 경우에만 만듭니다.
페이지 내부의 기법·고유 형식이 미지정인 요청된 설명 페이지는 맨 위 결론 → baoyu식 AI 일러스트레이션 한 장 → 부연 2~4줄 → 아래 접이식 근거로 시작합니다. 한 장은 여러 패널·그림을 자동 증식하라는 뜻이 아닙니다. 중요한 한정 조건과 미확인 사항은 접기 전에도 보이며, 상세 출처·재현 정보는 아래 `<details>`에 둡니다. 질문 하나를 다루면 그림 한 장·한 줄 설명·근거·요청을 기본 단위로 삼고, 요청할 사항이 없으면 억지로 만들지 않습니다. 여러 내용 주제는 주제마다 한 섹션·3~5문장 이내를 초기 상한으로 제안하며 필요한 한정 조건은 보존합니다. 일반 대화에는 이 파일 구성을 적용하지 않습니다.
AI 일러스트레이션, `baoyu` 같은 결과물, 캐릭터·손그림 일러스트레이션과 위 기본 페이지의 그림에는 [래스터 일러스트레이션](raster-illustration.md)을 읽습니다. 이용 가능한 이미지 도구가 있으면 실제 래스터를 생성합니다. 도구 부재에는 완성한 baoyu식 프롬프트를 우선 권장하고, SVG→PNG를 `임시 대체물, baoyu 생성본 아님`으로 구분해 함께 제공합니다. 이를 AI 래스터 생성 성공으로 보고하지 않습니다. 독립 이미지 요청은 형식 축이 결정되며, 페이지 안의 한 그림은 페이지 전체를 F3로 바꾸지 않습니다.
한국어 설명은 일반 HTML 셸을 기본으로 합니다. archify 패널 보드는 구조 도해가 설명의 중심일 때만 선택하며, 단순 관계·흐름 언급만으로 보드로 바꾸지 않습니다. 명시적으로 선택한 기법·형식은 보존하되 실제 표현 가능성을 확인하고, 충돌하면 미충족 요구만 확인합니다. 선택된 archify에는 explainer 페이지 레이아웃을 사용합니다. 표·목록·일러스트레이션 중심은 일반 HTML을 사용합니다. 요청된 변형은 각각 렌더러 계약에 따른 고유 형식을 사용합니다. archify 변형은 최대 하나만 포함합니다.
archify 분기에서는 컴포넌트, 호출, 상태와 데이터 흐름에 기본 다이어그램을 사용합니다. 한국어에서는 고정 범례 문제를 피하도록 `@workflow` 대신 `@architecture`를 사용하되, 순서·분기·조건을 보존할 수 있는지 확인하고 불가능하면 해당 요구를 차단하고 일반 HTML에서 정확히 표현하는 안을 제시합니다. 이미 선택된 렌더러를 말없이 전환하지 않습니다. 고정 영문 UI의 한국어 치환은 선택적인 전달본 후처리이며 원본과 receipt를 보존합니다. 치환본을 원본 finalize 통과 바이트로 주장하지 않습니다. 장면, 공간 관계나 물리적 배치에는 [장면 그림](../../tk-writing/references/scene-figures.md)을 읽습니다. archify는 변환한 PNG를 `@image`, 대체 텍스트와 캡션으로 삽입하며, 기법별 HTML은 공통 계약에 따라 원래 인라인 SVG를 유지할 수 있습니다. 입력 변화가 메커니즘을 설명하면 비교 가능한 상태를 두 개에서 네 개까지 보여 줍니다. 실제 공간 장면을 순서도로 대체하지 않습니다.
레이블, 상태 전이와 설명을 일치시키고 제공된 기하 구조와 입력을 보존합니다.

명시적 요청이나 추천 선택에 따라 실시간 상호작용을 제공하면 [대화형 예시](../../tk-writing/references/interactive-examples.md)를 읽습니다. archify에는 지원되는 기본 상호작용을 사용합니다. 일반 HTML과 선택한 기법별 HTML은 공통 계약에 따른 인라인 향상을 사용할 수 있습니다. 이미지 도우미는 그림을 만들며 필수 페이지 틀을 만들지는 않습니다.
독립적으로 반복 재생되는 SVG를 명시적으로 요청하면 [애니메이션 SVG](animated-svg.md)를 사용합니다.
동영상을 선택하면 [동영상 출력](video-output.md)을 읽고 `tk-video`에 인계합니다.
어느 출력 선택도 근거 의무를 바꾸거나 발행을 승인하지 않습니다.

이미 만든 설명 페이지·studio의 피드백을 받으면 원본 페이지·위치 ID·확인된 원고와 현재 권한을 대조합니다. archify는 생성 HTML을 직접 편집하지 않고 원고와 `patch explainer` 절차에서 수정하여 재생성·검사하고 새 studio를 만듭니다. 원고 경로가 없으면 먼저 현재 승인 범위에서 조사합니다. 전달용 studio에는 `--owner-skill tk-explain`과 확인한 원고의 `--source-path`를 넘깁니다.
확인한 결함은 현재 승인 범위에서 전달본까지 수정합니다. 사용자의 회고·upstream 보고 예정은 수정 보류 지시가 아닙니다. 명시적으로 수정을 보류했거나 새 권한이 필요한 경우에만 해당 수정을 멈춥니다.
