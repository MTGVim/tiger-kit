# 동작 검증

<a id="exact-target-and-trusted-input"></a>
## 정확한 대상과 신뢰할 수 있는 입력

정확한 컨트롤을 식별합니다. 해당 컨트롤이 없으면 비슷한 레이블의 버튼을 반복해서 찾지 말고
모드, 탭, 스크롤과 토글 상태를 확인합니다.

클릭 전달을 비교할 때는 부작용이 없는 컨트롤을 선택합니다. 클립보드, 파일 또는 알림에 쓰기 전에
[사용자 공유 상태 안전 기준](../../tk-verification-guidance/references/verification.md#user-shared-state)을 적용합니다.
headless 입력은 사용자의 시스템 클립보드나 파일을 격리하지 않습니다.

제공자의 네이티브 신뢰 포인터·키보드 API를 사용합니다. `evaluate_script`는 상태, 계산된 값 또는
좌표를 관찰할 때만 사용합니다. `element.click()`, `form.submit()` 또는 `dispatchEvent()`를
상호작용 근거로 취급하지 않습니다.

새로 구현한 직접 입력 도우미는 광범위한 캡처에 앞서 안전한 대상 컨트롤 하나에서 필요한 동작과
관찰된 사후 조건을 먼저 입증합니다. 이벤트 수신만이 아니라 네이티브 기본 동작을 관찰합니다.
Space 동작이 통과해도 Enter 동작의 실패가 해결되지는 않습니다. 원래 입력을 수정하여 재생하거나,
별도 검증 범위로 구분하여 미검증 상태로 유지합니다. 한 제공자의 이벤트 페이로드를 보편적인 규칙으로
복사하지 않습니다.

양식 값은 신뢰할 수 있는 키보드 입력으로 입력하며, 네이티브 날짜/선택 컨트롤은 눈에 보이는
키보드 또는 포인터 동작으로 조작합니다. `maxLength` 같은 제약을 우회하거나 네이티브 컨트롤
동작을 실행하지 않을 수 있는 DOM 값 할당이나 스크립트 입력을 사용하지 않습니다. 제공자의
`fill` 작업을 사용한다면 사용자와 동등한 신뢰 입력을 생성하고 컨트롤의 제약을 준수하는지 먼저
확인합니다. 그렇지 않으면 키보드로 입력합니다. 결과로 표시된 값을 확인하고, 저장 흐름에서는
캡처한 요청 본문도 확인합니다.

변경이 이루어졌다고 주장하려면 관련 네트워크 요청과 응답이 필요합니다. 인수 검증은 하나의
흐름에서 UI 전환, 요청/응답과 최종 UI 상태를 연결합니다. 응답, 토스트 또는 로컬 DOM 변경만으로는
충분하지 않습니다.

저장 흐름에서는 리디렉션, `history.back()`과 bfcache 복원 후에도 기록이 남도록 페이지 JS 문맥이
아닌 제공자 측 기록기를 사용합니다. Playwright CLI에서는 같은 세션의 공식 `run-code`로 동작 전에
`page.on('request')`, `response`, `requestfailed`를 관찰하고 method·안전한 path·status·실패 이유와
허용 목록에 포함된 비민감 본문 필드만 보존합니다. 헤더나 필터링하지 않은 페이로드는 출력하지 않습니다.
기본 쓰기 차단에는 요청을 보내는 동작 **전에** `page.route` 또는 필요한 컨텍스트 route를 설치하여
정확한 요청을 가로채고 `route.abort()`로 전송 방지를 확인합니다. Service Worker 등으로 차단을
보장할 수 없으면 요청을 유발하지 않고 `Unverifiable`로 남깁니다. 페이로드 구성만 입증한 실행은
`blocked-intercept`이며 실제 저장 성공이 아닙니다. 정확한 저장이 승인되면 요청/응답 쌍과 새 진입
페이지의 필드를 다시 읽어 저장 결과를 확인합니다. 실패·예외 경로에서도 관찰자와 route를 제거합니다.

선택된 제공자의 신뢰 입력 API를 사용합니다. **Playwright CLI를 선택한 경우에만**
SortableJS와 네이티브 HTML Drag & Drop에 먼저 CLI `drag <startRef> <endRef>`를 사용하고
실제 순서·대상 상태와 필요한 요청을 확인합니다. 두 구현을 동일하게 가정하지 않습니다. 실패하면
같은 세션의 공식 `run-code`에서 `locator.dragTo` 또는 실제 `page.mouse` 이동/누르기/떼기를
검증합니다. DOM 순서 변경이나 합성 drag 이벤트를 실제 입력 성공으로 계산하지 않습니다.
다른 제공자를 명시했다면 CLI를 실행하지 않고 해당 제공자의 입력·관찰 경계를 유지합니다.
같은 최소 사례에서 모두 실패했다면 실패한 입력·기하·최종 상태·요청을 보존하고 해당 drag를
`Unverifiable`로 남깁니다. 이 실패만으로 직접 CDP 연결·별도 MCP·브라우저 추가 실행이나
실제 변경 시나리오 재생을 허용하지 않습니다. 별도 경로는 구체적인 기능 공백과 정확한 승인을
확인한 뒤에만 검토합니다. 일반 drag에 직접 프로토콜 명령을 요구하지 않습니다.

2026-11-03의 `@playwright/cli@0.1.23` / Playwright `1.65.0-alpha-2026-10-30` /
Chrome `156.0.8078.74` 로컬 fixture에서 SortableJS `1.15.6`과 네이티브 HTML Drag & Drop을
각각 검증했습니다. CLI `drag`, 같은 세션 `locator.dragTo`와 실제 `page.mouse` 입력 모두
Sortable 순서 `[a,b,c] → [b,c,a]`, native drop 값 `local-item`, 각 POST 본문과 성공 응답을
확인했습니다. 기존 intercepted CDP 비교도 실제 `dragIntercepted`의 DragData를 받아 두 fixture의
같은 최종 상태와 POST/200 응답을 통과했습니다. 단순 CDP mouse 비교에서는 Sortable이 `[b,a,c]`여서
실패했으므로 이를 CDP 자체의 불가능성으로 해석하지 않습니다. CLI 경로가 필요한 상태와 요청을
모두 충족했기 때문에 일반 drag의 직접 CDP 지침을 제거합니다. 이 표본은 임의의 drag 구현에 대한 보장이 아닙니다.

headless 모드에서 신뢰 키보드 선택을 무시하는 닫힌 네이티브 `<select>`에는 문서화한 입력 한계의
대응으로만 제공자의 옵션 선택 또는 `change` 전달을 사용합니다. 결과 요청과 UI 상태를 독립적으로
검증하며 이 우회 방법을 신뢰할 수 있는 사용자 입력으로 설명하지 않습니다.

<a id="conditional-state-and-dialogs"></a>
## 조건부 상태와 대화상자

특정 API 상태에서만 UI가 나타나면 실제 전송이나 저장보다 `initScript` 응답 mock을 우선합니다.
애플리케이션이 실제로 파싱하는 envelope에 맞추며, 형태를 추측하지 말고 소스 매핑을 확인합니다.

상호작용 전에 네이티브 alert/confirm 핸들러를 설치합니다. 차단 대화상자가 이미 열려 있으면
수락하거나 닫은 뒤 계속합니다.

<a id="motion"></a>
## 모션

제공자의 단발 스냅샷에 애니메이션이 없다는 이유만으로 애니메이션이 존재하지 않는다고 추론하지 않습니다.
트리거 전에 `animationstart`, `animationend`, `transitionstart`, `transitionend`와 필요한
`MutationObserver`를 등록하고, 신뢰 입력 후 하나의 이벤트 타임라인을 확인합니다.

합성 DOM probe는 순수 CSS 계산에만 유효합니다. 프레임워크의 mount/unmount 수명주기가 중요하면
실제 컴포넌트 렌더링 주기로 재생하여 검증합니다.

<a id="clearing-fields"></a>
## 필드 비우기

제공자의 `fill(uid, "")`이 값을 지우는지 검증합니다. 빈 값 채우기가 아무 효과도 없다면
비어 있지 않은 값을 채운 뒤 신뢰할 수 있는 Backspace를 사용하거나, 필드 끝에서 실제 문자마다
Backspace를 한 번씩 보냅니다. 저장하기 전에 값이 비었는지 다시 관찰합니다.

네이티브 날짜 선택기에서는 신뢰할 수 있는 포인터 입력으로 날짜를 선택합니다. DOM 평가로
컨트롤 값을 설정한 뒤 이를 상호작용 근거로 계산하지 않습니다.
