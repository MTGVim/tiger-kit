# 인수인계 재개

명시적인 `resume`에만 읽습니다. 제품, Git이나 원격 변경을 승인하는 것은 아닙니다.

## 스냅샷 찾기와 선택

`resume <path>`는 사용자가 지정한 정확한 Handoff를 읽습니다. 경로를 주지 않았다면 **현재 Git worktree 루트**에서 `.tigerkit/handoffs/` 아래 `YYYYMMDD-HHmmss-<topic>.md` 형식의 일반 파일을 찾고, 과거 `.tigerkit/handoff.md`가 존재하면 레거시 후보로 함께 포함합니다. 다른 worktree, 저장소, 채팅 세션, 원격 PR을 목록 확보 목적으로 탐색하지 않습니다. `.strategy.md`, 임시 파일, 심볼릭 링크, 디렉터리는 후보에서 제외하며 내용 읽기 전 안전한 실제 경로를 확인합니다. 파일명만으로 현재 작업의 정체성이나 권한을 판단하지 않습니다.

- **0개**: 재개할 파일이 없다고 알리고, 파일 생성·실행을 가장하지 않습니다. 필요하면 기존 파일의 정확한 경로를 요청합니다.
- **1개**: 해당 파일을 자동 선택하고 현재 상태와 대조한 다음 재개합니다.
- **2개 이상**: 후보마다 **작성 일시(시간대 포함), 주제, 상태, 정확한 경로**를 확인해 최근 작성순으로 표시하고, [질문 라운드](../../tk-questioning/references/questions.md)에 따라 어느 파일을 재개할지 물어봅니다. 사용자가 선택하기 전에는 파일을 갱신하거나 실행을 시작하지 않습니다. 가장 최근 파일이라고 임의 선택하지 않습니다.

기존 `.tigerkit/handoff.md`에 작성 시각·주제가 기록되지 않았다면 `미확인`으로 보여주고 파일명·현재 mtime만으로 확정하지 않습니다. 후보가 복수라면 어떤 문서든 내용과 worktree 식별자를 간략히 대조해 다른 세션의 작업을 임의 합치지 않습니다. 선택 후 경로를 다시 읽고 아래 변동 분류로 이어갑니다.



`resume`은 `handoff snapshot`을 현재 Git 및 파일과 비교하여 작업을 재개하도록 요청합니다. 과거 `Goal run:`이 있는 Handoff는 기존 실행 기록으로 취급합니다. 기록과 실제 쓰기 종료 여부를 확인해 사용자에게 이관 필요성을 알리되, 폐기된 `tk-goal`을 재개하거나 일반 Handoff를 근거로 해당 실행의 제품 변경을 시작하지 않습니다.

먼저 다음을 새로 읽습니다.

- 선택했거나 명시한 **정확한** Handoff와, 참조되어 있다면 해당 작업에 연결된 Seed를 읽습니다. 그렇지 않으면 독립적인 no-Seed 계약을 읽습니다. `resume <path>`를 다른 후보나 최신 파일로 대체하지 않습니다. 기록된 worktree 절대 경로가 현재 경로와 다르면 조용히 합치지 않고 차이를 확인합니다. 다른 worktree에 옮겨 재개하려는 명시적 의도가 없으면 중단하여 필요한 결정을 묻습니다.
- Handoff에 `Strategy:`가 있으면 정확한 경로와 [장기 전략](strategy.md)을 읽고 전체 목표, 마일스톤, 판단 이유 및 실패 근거를 복원합니다. 누락·충돌한 전략은 추측으로 재구성하지 않습니다. `Goal run:`이 있으면 원래 실행의 상태·승인·Git 근거만 대조하고, 쓰기가 끝나지 않았다면 새 작업을 시작하지 않습니다. 외부 실행기로 옮기려면 별도로 계획을 준비하고 승인받습니다.
- `branch`/`HEAD`/`worktree`
- 변경 파일
- 관련 검증 근거
- 다음 승인된 행동이 해당 PR에 의존할 때만 정확한 현재 원격 상태를 읽습니다. 다른 열린 PR을 탐색하지 않습니다.

`Next step`을 실행하기 전에 `Owner skill`을 현재 설치된 소유자에서 다시 읽고 생성·검증·전달의
남은 단계를 따릅니다. 렌더러 명령이나 이전 시범 스크립트는 담당 스킬의 후처리 단계를 대신하지 않습니다.
기존 Handoff에 필드가 없으면 연결된 산출물·원천에서 담당자를 확인합니다. 확인되지 않으면 임의의
렌더러를 실행하지 않고 해당 재개 분기를 `Unverifiable`로 남깁니다. 일반 작업으로 담당 스킬이 없다면
`none`을 명시하고 기존 계약으로 계속합니다. 로딩 자체는 새 변경·설치·발행 권한을 부여하지 않습니다.

그런 다음 변동을 분류합니다.

| 분류 | 행동 |
| --- | --- |
| 없음 | `Next step`부터 추가 질문 없이 계속하되, `Next step`이나 `Open questions`가 여전히 사용자 결정을 기다리는 경우는 예외입니다. 사용자 결정을 기다리는 경우에는 질문 전에 [질문 라운드](../../tk-questioning/references/questions.md)를 읽고, 그 미결 결정을 네이티브 질문 도구 또는 채팅 대체 형식으로 전달하여 재개 보고를 끝냅니다. |
| 비본질적인 `drift` | 기록하고 계속합니다. |
| 중대한 진행 상황 `drift` | 현재 근거로 `Handoff`를 갱신하고 필요한 결정만 확인합니다. |
| `Seed` 계약 `drift` | `Handoff`에서 해결하지 말고 `tk-prep`으로 다시 진입해야 한다고 보고합니다. |
| 충돌 | 양립할 수 없는 근거를 제시하고 `Blocked`로 표시합니다. |
| 미검증 | 필요한 상태를 확인할 수 없으면 `Unverifiable`로 표시합니다. |

`resume`은 작업을 계속하도록 승인할 수 있지만, `Seed`의 `goal/scope/decision/AC` 변경 승인이나 원격 발행 권한을 대체하지 않습니다.
