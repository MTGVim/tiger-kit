# 독립 리뷰 프로토콜

모든 직접 실행의 정확한 변경 리뷰, SDD Unit 리뷰, SDD 전체 변경 리뷰 또는 명시적 `tk-review` 리뷰에서 읽습니다. 컨트롤러는 대상 결합, 디스패치, 취합, 후보 검증, 수정 라우팅과 최종 출력을 담당하며, 결과를 수락하기 전에 [리뷰어 근거와 복구](review-operations.md#reviewer-evidence-and-bounded-recovery)를 읽습니다. 탐색 리뷰어와 발견 사항 검증자는 읽기 전용 리프이며 재디스패치하지 않습니다.

<a id="delegation-permissions"></a>
## 위임 권한

컨트롤러는 자식 디스패치 전과 접근·환경이 바뀐 재개 전에 [위임 권한](delegation-permissions.md)을 읽고 부모와 같거나 더 좁은 실효 접근을 검증합니다. 입증하지 못하면 해당 디스패치를 중단합니다. 리프는 브리프의 검증된 경계를 지키며 불일치가 있으면 반환합니다.

컨트롤러는 리뷰·검증 리프를 디스패치·재개·교체·재시도하기 전에 [위임 예산](delegation-budget.md)을 읽습니다. 브리프의 조사 확대·완료·중단 조건과 누적 제한은 필수 검토 범위를 줄이지 않습니다. 한도에 도달하면 미검토 범위를 반환하며 이를 `Pass`로 바꾸지 않습니다.

<a id="inputs-and-evidence-authority"></a>
## 입력과 근거의 권위

저장소 지침, 작업이나 계획이 프로젝트 규칙을 명시하면 [프로젝트 규칙 선택](project-rules.md)을 읽습니다. 준수 여부를 판정하기 전에 실제 diff와 고정된 기준선에 비추어 선택을 재검증합니다.
선별된 기여 규칙이 있으면 direct·SDD Unit·전체 변경의 각 독립 리뷰어에게 출처·적용 조건·요구 행동·
실행 근거와 기록 수집 범위를 함께 전달하고 같은 문서의 [작업 과정 판정](project-rules.md#contribution-process-evidence)을 적용합니다.
최종 코드 판정과 과정 준수를 구분하며 근거 누락을 위반이나 통과로 바꾸지 않습니다.

모든 리뷰 역할을 동일하고 정확한 저장소·범위 또는 worktree 지문, 존재하는 경우 원래 작업이나 사건, 예상 시나리오, 승인된 결정과 AC, 저장소 규칙, 정확한 diff와 해당 정확한 대상에 대해 이미 수집한 테스트·빌드·런타임·브라우저 근거에 결합합니다. 사용자에게 보이는 출력이 바뀌는 경우에는 승인된 표시 필드·문구·조건별 상태의 전체 목록과 `이 밖의 표시 항목 없음`을 리뷰어 브리프에도 동일하게 전달합니다. 실제 출력과 이 목록을 대조해 빠진 항목과 승인 범위를 넘어 추가된 표시 항목을 모두 Spec/AC 이탈 후보로 검사합니다. 근거에는 명령, 출력과 종료 상태를 포함합니다. 재실행을 고려하기 전에 이 근거를 읽습니다. 오래되거나 누락된 근거는 공백이며 통과 주장이 아닙니다.

컨트롤러가 리뷰 전달 형식을 선택할 때는 [산출물 전달](sdd-transport.md)을 읽습니다. 짧은 계약·판정과 큰 diff·로그를 구분하며, 파일 전달도 동일 후보·환경·명령·실행 조건의 근거만 재사용합니다. 후보나 조건이 바뀌거나 구체적인 의문이 있으면 필요한 재검증을 수행합니다.

제공된 diff가 파일 경로이면 `diff --git` 경계를 검사하고 현재 도구의 읽기·출력 한도 안에서 필요한 각 섹션을 한 번씩 나누어 읽습니다. 너무 큰 파일 섹션은 hunk 경계에서 나눕니다. 필요한 모든 hunk, 이름 변경, 바이너리 변경 고지와 파일 간 위험 경계를 유지합니다. 리뷰어는 디스패처가 고른 파일 일부를 완전한 검토 범위로 받아들이지 말고 관련 섹션을 직접 선택합니다. 이미 제공된 인라인·읽기 콘텐츠를 재사용합니다. 한도를 우회하려고 Git으로 전체 diff를 재생성하거나 전체 파일 읽기를 반복하지 않습니다. 특정 관계, 발견 사항 검사 또는 유실·잘린 맥락은 한정된 재읽기의 근거가 될 수 있습니다. 이유를 명시하고 누락된 섹션만 복구합니다. 불완전한 검토 범위는 `Unverifiable`로 남으며 비용 절약을 위한 Pass가 될 수 없습니다.

구현을 담당하는 흐름에는 실제로 바뀐 동작, Seed 이탈과 이유, 새로 발견한 위험, 검증 관찰과 미해결 한계를 명시하는 구현 후 회고를 추가합니다. 이를 원래 동작, 승인된 결정, 저장소 계약, 정확한 코드·diff와 런타임 근거보다 낮은 신뢰할 수 없는 주장 묶음으로 취급합니다. 독립 실행 리뷰는 회고 없이도 유효하며 의도를 만들어 내는 대신 누락된 의도를 공개합니다.

각 탐색 리뷰 역할은 먼저 회고 없이 원래 근거와 정확한 변경을 받아 검사합니다. 관찰을 기록한 뒤 같은 읽기 전용 리프를 회고와 함께 재개하여 중요한 주장을 확인하거나 반증하게 합니다. 초기 payload에는 회고를 넣지 않으며 구현자 논리나 주장된 테스트 성공을 증거로 사용하지 않습니다.

아래의 1인 조건을 충족한 direct 또는 명시적 `tk-review`에서만 회고 재개를 생략할 수 있습니다. 컨트롤러가 회고의 모든 주장을 해당 리뷰어가 이미 기록한 관찰·인용과 대조하여 같은 내용을 확인하고, 새 주장·이탈·위험·불확실성이나 미해결 발견 사항이 없을 때 적용합니다. 대응 근거와 생략 이유만 짧게 기록하며 구현자의 자기평가로 빈칸을 채우지 않습니다. 하나라도 대응하지 않거나 더 엄격한 요구가 있으면 재개합니다. 이 예외는 최초 블라인드 검토, 두 판정 축, 별도 후보 검증이나 SDD 리뷰의 회고 확인을 면제하지 않습니다.

리뷰어와 검증자는 전체 테스트 모음·빌드·개발 서버 같은 공유 무거운 프로세스를 시작하지 않습니다. 기존 근거로 해결되지 않는 질문은 컨트롤러에 반환합니다. 집중 실행이 필요하면 컨트롤러가 [실행 예약과 대기](review-operations.md#review-processes)에 따라 먼저 예약해야 합니다.

<a id="discovery-seats-and-walks"></a>
## 탐색 리뷰 역할과 검토 경로

하나의 리뷰 역할은 두 판정 축과 두 절차적 검토 경로를 모두 완료합니다.

1. **충실도·재현**: 원래 사건이나 예상 시나리오를 재현합니다. AC 누락, 과도한 동작, 구현 이탈과 보호가 실제 동작을 다루는지 확인합니다.
2. **변경 위험**: 제거된 동작이나 `must-not-change` 동작, 오류·상태·생명주기 경로, 호출자·피호출자와 생성자·소비자 계약 및 변경에 귀속되는 횡단 위험을 검사합니다.

변경이 스킬 지침을 상당 부분 다시 쓰거나 이동한다면 기존 독립 리뷰 역할이 이전 텍스트와 대조하며 맥락 속에서 변경된 문장을 읽게 합니다. 본문을 재구성한 경우 항상 불러오는 본문 전체와 이동된 섹션을 읽습니다. 복사된 텍스트는 한 번 검사합니다. 행위자, 조건, 예외, 승인 권한, 실패 상태나 규칙 우선순위를 모호하게 만드는 문구를 인용하고 바뀐 동작을 보여 줍니다. 의도하고 승인한 계약 변경과 우발적인 의미 변화를 구별합니다. 명확한 문구와 명시적인 미확인 사항은 유효합니다. 문체 선호만으로는 발견 사항이 아닙니다. 다시 압축하기보다 누락된 의미를 명료하게 복구하거나 배치와 읽기 조건을 수정합니다. 동작 계약에 영향을 주지 않는 작은 편집에는 추가 읽기 검토가 필요하지 않습니다. 이는 충실도·재현과 변경 위험 검사의 일부이며 추가 리뷰 역할이나 `tk-rewrite` 호출이 아닙니다.

변경 위험 검사 중 diff가 문자열 형태(이름 일치, 접두사·접미사, 분할, 경로 위치, 복합 키나 정규화한 키)에서 식별 정보, 소유권, 출처 또는 라우팅을 도출한다면 실제 술어가 혼동하는 서로 다른 유효한 개체 두 개를 구성하고 그 결정을 추적합니다. 충돌 여부만 묻고 멈추거나 브리프가 해당 조회를 요청했다는 이유로 오식별을 받아들이지 않습니다. 집중 회귀 근거가 관찰 가능한 분리를 보호하는지 확인합니다. 기존 정본 식별 정보, 명시적 필드 또는 모호하지 않은 표현을 우선합니다. 표시 전용 서식, 직접 비교하는 정본 타입 ID와 검증된 단사 저장소 계약에는 충돌 검사가 필요하지 않습니다. 새 리뷰 단계 없이 기존 검토 경로 안에서 수행합니다.

SDD Unit 리뷰는 새로운 탐색 리뷰 역할 하나를 사용합니다. 직접 실행 최종 리뷰와 명시적 `tk-review`는 정확한 diff와 근거로 범위가 한정되고 가역적인 변경, 이해된 호출자, 집중된 동작 보호 또는 정당한 테스트 `N/A`, 중대하고 미해결된 위험의 부재가 입증될 때만 새로운 탐색 리뷰 역할 하나를 사용합니다. 보안·권한, 영속 데이터나 마이그레이션, 공개 계약 호환성, 경계를 넘는 상태·생명주기 또는 복잡한 상호작용이 있는 direct 또는 명시적 `tk-review` 대상에는 맥락이 격리된 탐색 리뷰 역할 두 개를 사용합니다. 알 수 없는 영향이나 필수 테스트 예외도 두 개를 요구합니다. 파일 수가 적거나, `direct`라는 표시가 있거나, 리뷰어 자원이 부족하다는 사실은 낮은 위험을 입증하지 않습니다. 더 엄격한 승인된 리뷰 요구나 저장소 리뷰 요구를 준수합니다. 중대한 변경 후 정확한 후보를 재평가하고 한 역할의 조건이 더 이상 성립하지 않으면 검토 범위를 늘립니다.

SDD 전체 변경 최종 리뷰는 계속 맥락이 격리된 탐색 리뷰 역할 두 개를 사용합니다. 각 역할은 같은 대상, 근거, 판정 축, 발견 사항 기준과 심각도 기준을 사용하고 두 검토 경로를 모두 완료합니다. 두 역할에서는 하나가 충실도·재현으로 시작하고 다른 하나가 변경 위험으로 시작합니다. 어느 쪽도 반환 전에 상대의 발견 사항이나 판정을 보지 않습니다. 한 역할이어도 사전 정보 없는 검토, 위 조건에 따른 회고 확인과 보고 가능한 후보의 별도 검증이 필요합니다.

현재 호출은 대상을 작성하거나 수정하지 않았고 다른 역할의 결과를 보지 않은 경우에만 최종 리뷰 역할 하나를 맡을 수 있습니다. 구현 또는 컨트롤러 맥락은 독립 리뷰 역할이 될 수 없습니다. 호스트가 필요한 새 맥락을 제공하지 못한다면 가능한 가장 강한 정확한 범위의 리뷰를 수행하고 근거 있는 결함을 보고하며 누락된 독립 검토 범위를 `Unverifiable`로 표시합니다. 한 맥락의 직렬 검토가 독립적이라고 주장하지 않습니다.

`appear | disappear | change | preserve | defect-fix` 의도를 사용합니다. 새 기능이나 리팩터링에 이전 사건을 만들어 내지 않습니다. 예상 시나리오와 `must-not-change` 지점을 사용합니다.

<a id="aggregation-and-candidate-verification"></a>
## 취합과 후보 검증

탐색 후보의 합집합을 취합합니다. 깨끗한 결과를 낸 역할이 다른 역할의 후보를 취소할 수는 없습니다. 근거로 동일한 인과적 근원, 수정 경계와 실패 유형이 입증될 때만 중복을 제거합니다.

`Critical | Important`로 보고할 수 있는 모든 후보를 새로운 검증자에게 보냅니다. 완전한 주의 집중을 위해 필요한 경우에만 분할하고 보고 가능한 발견 사항 수에 상한을 두지 않습니다. 검증자는 해당 경로를 막는 가드, 그 상태를 불가능하게 하는 불변식, 런타임 관찰 증거 또는 동작이 변경되지 않았고 관찰 불가능하다는 증명처럼 직접적인 반대 근거가 있을 때만 후보를 기각할 수 있습니다. `Speculative`, 확신도만의 판단 또는 다른 역할의 `Pass`는 기각 사유가 아닙니다.

검증된 후보를 보고합니다. 검증으로 중요한 후보를 확인하지도 반박하지도 못하면 정확한 불확실성을 `Unresolved`에 유지합니다. 확신도를 표현하기 위해 심각도를 낮추지 않습니다.

<a id="evidence-only-response-to-a-reported-finding"></a>
## 보고된 발견 사항에 대한 근거만의 응답

리뷰 대상이 바뀌지 않은 상태에서 구체적인 반대 근거로 발견 사항을 반박할 때만 컨트롤러와 새 검증자는 [근거만의 응답](review-operations.md#evidence-only-response-to-a-reported-finding)을 읽습니다. 구현자나 컨트롤러가 직접 기각하지 않으며 독립 검증 전에는 발견 사항을 열린 상태로 유지합니다.

## 범위·단순성과 수렴

각 변경 파일이 요청 목표·AC와 어떻게 이어지는지 한 문장으로 설명할 수 있는지 확인합니다.
연결되지 않는 변경은 범위 이탈 후보이며, 승인된 필수 선행 리팩터링은 이유와 근거로 구별합니다.
제거해도 목표가 성립하는 추상화·옵션·설정 계층을 찾아 실제 복잡성·유지 비용을 판단합니다.
스타일 취향이나 단순히 파일 수가 많다는 이유로 결함을 만들지 않습니다.
리뷰·수정 라운드가 세 번을 넘기려 하면 반복 원인과 접근 방식을 재검토합니다. 해결하지 않은
중요 finding을 통과시키거나 필수 독립 검토를 면제하지 않습니다. 같은 라운드를 무한 재시도하지
않고 범위·판정 기준의 불일치와 남은 문제를 담당자에게 반환합니다.
