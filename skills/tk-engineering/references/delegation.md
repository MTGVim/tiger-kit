# 위임과 독립 평가

자식을 디스패치·재개·교체하거나 검수 결과에 따라 재수정할 때 읽습니다. 직접 작업과 SDD가 같은 계약을 사용합니다. 이 참조는 [위임 권한](delegation-permissions.md), 정확한 후보 결합, 필수 검증과 발행 승인을 대체하지 않습니다. 새 runner, hook, 전역 장부나 모델 라우터를 만들지 않습니다.

## 역할과 능력 요청

메인 컨트롤러는 사용자 의도·우선순위·승인 경계, 작업 분해, 인수 기준과 최종 판정을 담당합니다. 소스 조사, 구현, 반복 수정과 상세 검수는 해당 리프에게 맡깁니다. 자료를 전달하려고 컨트롤러가 같은 코드 분석과 리뷰를 먼저 끝내지 않습니다.

| 역할 | 요청할 능력 티어 | effort 초기값 | 승격 조건 |
|---|---|---|---|
| 컨트롤러 | 최상위 | medium | 서로 충돌하는 계약, 복잡한 설계 판단에는 high를 검토합니다. |
| 아키텍처·미지 문제 탐사 | 최상위 | 미검증 | 사용자 대응표를 따르고 복잡도·근거 부족에 따라 지원되는 상위 effort를 검토합니다. |
| Generator / Optimizer | 상위 | medium | 복잡한 상태·경계·통합 구현에는 high까지 올린 뒤 필요하면 최상위 티어를 검토합니다. |
| 독립 Evaluator | 상위 | medium | 보안·권한·영속 데이터·호환성·복잡한 동시성 또는 반복 결함에는 high 또는 최상위 티어를 검토합니다. |
| 좁은 사실 수집·기계적 검사 | 경량 | low | 출처 해석·상충 근거 판단이 필요하면 상위 티어로 올립니다. |

이는 비용 우월성이 입증된 고정 조합이 아니라 초기 운영 정책입니다. 기존 호스트와 사용자가 정한 **능력 티어 대응표**를 사용하며 공급자·실제 모델명을 스킬에 넣지 않습니다. 티어와 effort는 서로 다른 축입니다. 현재 세션의 모델을 변경했다고 주장하지 않습니다.

호스트에서 이름으로 선택할 수 있는 위임 대상은 `tier-light`, `tier-standard`, `tier-top`으로 통일합니다. 선택지형 호스트는 `light`, `standard`, `top`을 사용합니다. 각 대상의 모델과 effort는 사용자 설정에 둡니다. 선택 설치 가능한 tk-route-mode는 사용자가 명시적으로 호출하는 설정 스킬이며, 일반 위임에서 자동 호출하거나 설치하지 않습니다. 대응표가 티어별 effort 초기값을 정하면 위 표보다 우선합니다. `standard` 티어는 effort를 high까지 높이고 그 이상이 필요하면 `top`으로 승격합니다. `light`의 상한은 사용자 대응표에서 정합니다. 이는 사용자 제공 벤치마크에서 제안된 초기 정책이며 원본 수치를 대조하지 않았습니다. 실제 작업 성능이나 비용 우위를 보장하지 않습니다.

이름으로 위임할 때에는 별도의 모델이나 effort 인자를 넘기지 않습니다. 일부 호스트에서 호출 인자가 대상 정의를 덮어씁니다. 이름에 따른 위임 대상이 없거나 필요한 승격 설정을 지원하지 않으면 확인된 호스트 기능을 사용해 직접 지정하고, 실효값을 확인할 수 없으면 `unverified`로 기록합니다.

호출 직전에 실제 도구 스키마에서 모델 선택, effort, 재개, 읽기 전용 권한 지원을 확인합니다. 이름으로 설정된 위임 대상이 없거나 필요한 승격 설정을 지원하지 않는 직접 지정 분기에서만 지원되는 모델과 effort 필드를 확인된 대응표로 명시합니다. 필드 이름이나 상속 동작을 제공자에 관계없이 단정하지 않습니다. 직접 지정할 수 없는 축은 호스트 설정에서 확인한 실효값을 기록하고, 알 수 없으면 `unverified`로 표시합니다. 존재하지 않는 필드를 만들거나 프롬프트에 적은 희망값을 적용된 설정으로 보고하지 않습니다. 엄격한 비용·능력 제약을 확인할 수 없으면 해당 호출만 차단합니다.

## 자식 컨텍스트 최소화

자식 생성 시 기본값이 전체 대화 상속인지 호출 도구의 실제 스키마로 확인합니다. `fork_turns` 등 명시적인 선택 기능이 있다면 작업에 필요한 최소 대화만 전달하고, 생략 시 전체 상속이 되는 기본값을 그대로 사용하지 않습니다. 해당 기능이 없으면 별도의 간결한 브리프와 정확한 자료 경로를 사용하되 컨텍스트 격리를 검증하지 못한 사실을 기록합니다. 전체 이력이 필수인 경우에만 범위와 이유를 명시합니다.

역할이 바뀌는 복원·실행·리뷰·회고에는 기존 자식의 맥락을 무조건 재사용하지 않습니다. 독립 Evaluator에게는 최초 사용자 요구·금지·위험·AC, 정확한 후보와 검증 가능한 원본 근거를 먼저 전달합니다. 구현자의 해석·성공 선언·전체 대화를 기본 입력이나 판정 근거로 삼지 않습니다. 구현자 결론을 확인해야 할 때만 그 내용을 별도의 검토 대상으로 표시합니다. 자식 생성 인자와 실제 전달 항목, 역할별 누락·중복을 가능한 범위에서 확인하고, 관찰하지 못한 비용 절감을 실측으로 주장하지 않습니다.

## 작업 인계

명시적으로 승인된 목표 실행의 자식은 현재 목표·단계·실제 위임 범위에서 미결 결정과 실행 승인 요청을 부모에게 반환합니다. 부모는 관찰한 근거와 원래 사용자 승인에 비추어 대리 판단 가능 여부를 확인합니다. 대리 판단과 사용자 결정을 구분하고 실제 사용자 승인·호스트 권한을 대신하지 않습니다. 지원되는 재개 또는 새 자식 인계를 사용하되 이전 쓰기 종료를 확인합니다. 목표 실행 외 일반 위임의 권한은 변경하지 않습니다.

브리프에는 목표, 변경 허용 범위, 원래 요구·금지·사용자 고정 문구, AC, 정확한 workspace와 BASE 또는 입력 파일 지문, 진입점, 검증 방법, 역할·능력 요청, 종료 조건을 담습니다. 구현자는 승인된 범위에만 쓰고 리뷰어는 읽기 전용입니다. 동일 범위에 쓰는 구현자를 동시에 실행하지 않습니다.

짧은 반환은 `상태 / 후보 revision·지문 / 변경·판정 / 근거 경로 / 미해결 항목`으로 구성합니다. 큰 diff·로그·원문은 [산출물 전달](sdd-transport.md)에 따라 담당자에게 직접 제공합니다. 짧게 반환한다는 이유로 결함·불확실성·미검토 범위를 감추지 않습니다. 관측하지 못한 토큰 수와 비용은 추정 실측값처럼 적지 않습니다.

긴 피드백 목록은 기존 Seed나 실행 근거에 항목 ID, 요구·거절·금지, 반영 위치, 상태를 짧게 보존합니다. 수정 전과 전달 전에 대조하며 중복 입력은 합칩니다. 새 전역 장부나 모든 작업에 의무적인 파일을 만들지 않습니다. 미룬 항목은 이유와 남은 상태를 유지하며 완료로 바꾸지 않습니다.

## Evaluator–Optimizer 반복

1. Generator가 구현·자체 검사와 필요한 테스트를 끝내고 정확한 후보와 증거를 반환합니다. 자체 점검은 독립 검수가 아닙니다.
2. 독립 Evaluator가 원래 요구, 실제 diff 또는 최종 파일, 실행 증거를 먼저 확인합니다. 구현자의 성공 선언과 해석은 정답으로 취급하지 않습니다. [리뷰 프로토콜](review-protocol.md)의 두 판정 축과 발견 사항 기준을 유지합니다.
3. 실패하면 같은 종류의 확정 결함을 한 묶음으로 모읍니다. 각 항목에는 위치, 실제·기대 동작, 재현·근거, 심각도와 수정 후 확인할 조건을 담습니다. 미확인 의심과 취향은 확정 결함과 분리합니다.
4. 가능한 경우 기존 Generator를 재개해 Optimizer로 사용합니다. 재개가 지원되지 않거나 기존 맥락이 유실됐으면 현재 후보, 원래 계약, 열린 결함과 이미 시도한 접근을 새 구현자에게 전달합니다. 이전 구현자의 쓰기 종료를 확인하기 전 교체하지 않습니다.
5. 수정 후에는 새 독립 리뷰 맥락으로 열린 항목과 정확한 수정 diff, 직접 영향받는 경계를 재검수합니다. `ADDRESSED | NOT ADDRESSED`와 수정이 만든 새 결함을 반환합니다. 매번 전체 탐색을 다시 하거나 구현자의 판정을 재사용하지 않습니다. 마지막 통합 검토와 최종 후보 검증은 소유 업무의 의무대로 수행합니다.

### 반복의 종료

기본값은 **최초 구현 1회 + 재수정 최대 2회**입니다. 재수정 1회는 검수 피드백에 따른 한 번의 수정 인계와 그 결과의 독립 재검수입니다. 구현자 내부의 정상적인 TDD와 테스트 실행 횟수는 이 회차가 아닙니다. 2회는 업계 표준이나 성능 측정 결과가 아니라 TigerKit의 초기값입니다. 더 엄격한 사용자·저장소 제한은 보존합니다.

같은 실패를 새 근거·변경된 가설·검증 진전 없이 반복하거나 퇴행·중대한 위험이 생기면 한도가 남아도 같은 수정 인계를 멈춥니다. 최초 실패만으로 즉시 중단하거나 정상 RED·장시간 검사를 무진행으로 판정하지 않습니다. 상위 티어 진단·작업 재분해·구현자 승격은 승인된 범위에서 컨트롤러가 판단하며 매회 사용자에게 허락을 묻지 않습니다. 승격된 구현자의 수정도 같은 회차에 포함합니다.

한도에 도달하면 원인 진단과 다음 접근을 제시하되 동일 작업의 회차를 재개·교체·설계 재검토로 0으로 돌리지 않습니다. 새 시도가 필요하면 구체적으로 바뀐 가설과 추가 한도를 기존 작업 기록에 남기고 해당 업무의 승인 경계를 따릅니다. 확인된 AC 실패·보안 문제를 `Ruling:`만으로 Pass로 바꾸지 않습니다. 근거가 반증한 오탐과 승인된 범위 밖 제안만 각각 근거와 함께 닫거나 유예할 수 있습니다.

## 메인 직접 구현의 예외

컨트롤러의 직접 구현은 실패 후 자동 복구 경로가 아닙니다. 기존 구현자 수정, 원인 진단과 적절한 능력 승격을 먼저 검토합니다. 사용자가 직접 실행을 명시했거나 위임 도구가 없고 승인된 범위의 가역적인 작업을 진행해야 하는 경우에만 이유를 공개하고 직접 수행할 수 있습니다. 직접 수정에도 동일한 테스트와 **별도 독립 리뷰**가 필요합니다. 독립 맥락을 확보하지 못하면 자체 재독을 독립 리뷰로 부르지 않고 해당 관문을 `Unverifiable`로 남깁니다.

컨트롤러는 결과의 근거 결합과 필수 관문을 확인하되 코드를 전부 다시 읽는 중복 검수를 기본으로 하지 않습니다. 여러 작업 단위를 연속 실행하는 경우 다음 위임 전 안전한 작업 경계에서 [컨텍스트 보호](context-guard.md)를 확인하고 인계 조건이면 새 작업을 배정하지 않습니다. 위험이 높은 판단에 필요한 좁은 추가 확인은 생략하지 않습니다. 시작과 끝의 사용자 결정, 새로운 범위·권한·발행 승인은 유지하며 가역적인 중간 조정마다 사용자를 호출하지 않습니다.

## 실행량과 안전한 정지

현재 호스트가 실제로 관측·강제할 수 있는 턴, 호출, 경과 시간 또는 보고된 사용량으로 개별 작업과 전체 누적 실행량을 확인합니다. 재개·교체의 사용량을 0으로 초기화하지 않고 필수 검수·검증·인계 여유를 남깁니다. 강제 timeout과 프롬프트 권고를 구분하며 관측되지 않는 실시간 비용 한도를 보장하지 않습니다. 구현자는 한도 전에 새 작업을 멈추고 변경 파일, 검증 상태, 남은 일과 commit 상태를 반환합니다. 강제 중단은 안전한 checkpoint가 아니며 이전 쓰기 종료와 실제 후보를 확인하기 전 교체하지 않습니다. 읽기 전용 역할이 범위를 다 보지 못하면 미검토 범위를 반환하고 `Unverifiable`로 남깁니다. 새 영구 실행량 장부는 만들지 않습니다.
