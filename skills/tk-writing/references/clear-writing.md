# 명확한 글쓰기

사람이 읽는 설명, 문서, 채팅 문구에 이 기준을 적용합니다. 호출한 스킬의 목적, 출력 형식, 승인 범위가 이 기준보다 먼저입니다. 이미 잘 읽히는 글은 그대로 둡니다. 이 기준은 표현만 다루며, 글을 고친다고 새 사실이나 실행 권한이 생기지는 않습니다.

규칙과 함께 서로 다른 상황의 교정 예시를 제시합니다. 화살표 왼쪽은 다듬을 표현, 오른쪽은 같은 상황에서 더 명확하게 쓴 표현입니다. 괄호로 제시한 상황은 해당 예시의 전제입니다. 예시의 사실이나 문장 틀을 새 답변에 가져오지 말고 작성 원리를 적용합니다. 유지 예시는 원래 표현이 적절한 경우를 보여 줍니다.

## 1. 의미를 그대로 옮깁니다

<a id="meaning-before-polish"></a>
- **사실:** 원문과 확인된 근거에 있는 사건, 원인, 수치, 예시, 인용만 씁니다. 중요한 논점과 배경은 길어지더라도 남깁니다.
  - 예(응답 시간이 늘었지만 원인은 확인하지 못한 경우): "서버 과부하로 응답이 느려졌습니다." → "응답 시간이 늘었습니다. 원인은 확인하지 못했습니다."
  - 예(배송 예정일만 확인한 경우): "금요일에 도착합니다." → "안내된 배송 예정일은 금요일입니다."
- **주체:** 누가 했고, 누가 할 것이고, 누가 결정하고 승인하는지 문장에 드러냅니다. 확인하지 못한 주체는 "확인하지 못했습니다"라고 씁니다.
  - 예: "검토 및 승인 예정입니다. 담당자는 운영팀입니다." → "운영팀이 검토하고 승인할 예정입니다."
  - 예(삭제한 사람을 확인하지 못한 경우): "기존 파일은 누군가 삭제한 상태입니다." → "기존 파일이 삭제됐습니다. 삭제한 사람은 확인하지 못했습니다."
- **시점과 확실성:** 완료·진행·예정, 관찰·추정을 원문과 같은 강도로 씁니다. 능력·허가·의무·권고, 긍정·부정의 강도, 비교의 순위와 범위, 동시·배타·인과·조건 관계도 보존합니다.
  - 예: "수정 완료, 내일 배포 예정" → "수정은 마쳤고, 내일 배포할 예정입니다."
  - 유지(실제로 가능성만 확인한 경우): "이 설정이 오류의 원인일 수 있습니다."
- **근거:** 날짜, 수량, 단위, 기간, 분모, 링크, 인용은 그것이 뒷받침하던 주장과 함께 옮깁니다. 표와 그림의 참조 대상도 유지합니다. 독자가 따라갈 수 없는 내부 번호는 링크를 걸거나 무엇인지 풀어 씁니다. 둘 다 불가능하면 생략합니다.
  - 예(10월 요청 100건 중 95건 성공): "지난달 성공률 95%" → "10월에는 요청 100건 중 95건이 성공했습니다."
  - 유지: "2026년 10월 1일부터 7일까지 12건을 확인했습니다."
- **보호 대상:** 코드, API, JSON/YAML, 명령, 식별자, URL, 로그, 인용, 공식 명칭, 사용자가 정한 문구는 글자 그대로 둡니다. 코드 주석과 커밋 메시지는 저장소 관례를 따릅니다.
  - 유지: 정확한 응답 필드 `is_active`와 상태 코드 `403`은 그대로 쓰고 주변 설명에서 뜻을 풀어 줍니다.
- **맥락:** 사용자가 지정한 독자와 전달 상황을 우선합니다. 처음 읽는 독자에게는 필요한 배경을 남기고, 이미 같은 대화에서 공유한 배경은 줄입니다. 공유 여부를 확인할 수 없으면 확인된 배경을 남깁니다. 스타일 견본은 문장 리듬과 어조만 참고하고, 견본 속 사실은 가져오지 않습니다.
  - 예(프로그램을 설치한 폴더에서 실행해야 하고 독자가 설치 절차를 처음 보는 경우): "이대로 실행하세요." → "프로그램을 설치한 폴더에서 다음 명령을 실행하세요."

## 2. 결론과 사실로 시작합니다

- 첫 문장에 결론이나 확인한 사실을 씁니다.
  - 예: "문의하신 사항을 살펴본 결과, 예약 변경은 가능합니다." → "예약을 변경할 수 있습니다."
  - 예(사용 설명서 29행의 예시를 확인한 경우): "찾아보니 이 문구는 제가 지어낸 게 아니었습니다." → "이 문구는 사용 설명서 29행의 예시를 그대로 옮긴 것입니다."
- 사용자 말에 답할 때는 어느 경우에 맞고 어느 경우에 다른지 바로 씁니다.
  - 예(온라인에서만 자동 저장되는 경우): "절반만 맞아요." → "온라인에서는 자동으로 저장돼요. 오프라인에서는 직접 저장해야 해요."
  - 예(무료 버전은 단일 파일, 유료 버전은 동시 처리에 대응하는 경우): "정확히는 그렇지 않아요." → "무료 버전에서는 파일을 한 개씩 처리하고, 유료 버전에서는 여러 개를 동시에 처리할 수 있어요."
- 기준은 무엇이 들어가는지로 씁니다.
  - 예(실제 적용 할인만 계산하는 경우): "최대 할인을 가정하지 않습니다." → "고객이 실제로 쓴 할인만 뺀 금액입니다."
  - 예(집계 범위가 평일인 경우): "주말은 포함하지 않습니다." → "월요일부터 금요일까지 집계한 결과입니다."
- 조건이 있으면 어떤 조건에서 무엇이 달라지는지 씁니다.
  - 예(앱에서 변경한 값을 아직 저장하지 않은 경우): "저장된 내용 기준이라 앱과 다를 수 있습니다." → "저장된 값으로 셌습니다. 앱에서 아직 저장하지 않은 변경은 이 숫자에 빠져 있습니다."
  - 예(재고가 있을 때 당일 발송할 수 있는 경우): "상황에 따라 당일 발송이 가능합니다." → "재고가 있으면 당일 발송할 수 있습니다."
- 독자에게 할 일이 없으면 무엇을 끝냈는지 씁니다.
  - 예(수정·테스트·PR 발행을 실제로 마친 경우): "할 일 없음." → "수정과 테스트를 마치고 PR에 올렸습니다."
  - 예(접수가 끝났고 신청자에게 더 필요한 조치가 없는 경우): "추가 조치가 필요하지 않습니다." → "신청이 정상적으로 접수됐습니다."
- 실제 반론과 제한 조건은 내용 그대로 씁니다. 동의나 칭찬으로 문장을 여는 대신 그 근거가 된 사실을 씁니다.

## 3. 독자가 아는 말로 씁니다

- 가리키는 대상을 이름으로 씁니다. 독자는 쓰는 사람이 보는 화면을 보고 있지 않습니다.
  - 예(작성자 칸의 표시를 설명하는 경우): "지금은 위 행처럼 (관리자)와 숫자 ID로 보입니다." → "지금은 작성자 칸에 이름 대신 (관리자)와 숫자 ID가 나옵니다."
  - 예(이미지 크기를 줄이면 다운로드 시간이 줄어드는 상황): "그걸 바꾸면 빨라져요." → "이미지 크기를 줄이면 다운로드할 데이터가 줄어들어 더 빨리 열 수 있어요."
- 작업 과정을 보고할 때는 내부 단계, 하위 작업자, 모델 이름 대신 그 사실이 독자의 판단에 주는 영향을 씁니다.
  - 예(상태 변경만 확인했고 실제 산출물은 확인하지 못한 경우): "작업 상태를 Completed로 전이했습니다." → "작업 기록을 완료 상태로 바꿨습니다. 실제 수정과 검증 결과는 아직 확인하지 못했습니다."
  - 예: "하위 작업자의 검사 결과를 인수했고 실제 파일은 다시 확인하지 않았습니다." → "전달받은 검사 결과를 사용했으며 실제 파일은 다시 확인하지 않았습니다."
- 코드 조건식이나 필드 이름은 뜻으로 풀어 씁니다.
  - 예: `type === "ETC"` → "유형이 기타인 경우"
  - 유지(개발자가 구현할 조건 자체를 요청한 경우): `type === "ETC"`
- 독자가 처음 보는 용어는 처음 나올 때 한 구절로 뜻을 풀어 줍니다. 분야에서 굳은 용어는 그대로 씁니다.
  - 예(캐시의 TTL을 처음 접하는 독자): "TTL을 60초로 설정합니다." → "캐시 데이터를 유효하게 유지하는 시간(TTL)을 60초로 설정합니다."
  - 예(일상 용어): "수령처 변경이 가능합니다." → "물건을 받을 장소를 바꿀 수 있습니다."
- 제목과 라벨은 내용을 담은 짧은 명사구로 씁니다.
  - 예: "정해 주셔야 할 것" → "결정할 항목"
  - 예: "하루에 몇 건이 오나" → "하루 알림 건수"
  - 유지(사용자가 질문형 제목을 요청한 경우): "어떻게 시작하나요?"

## 4. 문장을 끝까지 씁니다

- 주어와 동사가 있는 문장으로 끝냅니다. 한국어에서 자연스럽게 빠지는 주어는 빼도 됩니다.
  - 예(결제 시도 횟수를 구분하는 값): "구분 값 필요" → "결제를 몇 번째 시도했는지 알 수 있는 값이 필요합니다."
  - 예: "예약 취소 후 환불 가능." → "예약을 취소한 뒤 환불받을 수 있습니다."
- 동작은 동사로 씁니다.
  - 예: "설정 변경 진행 후 배포 수행" → "설정을 바꾼 뒤 배포합니다."
  - 예: "담당자의 신청서 검토 및 결과 안내 예정" → "담당자가 신청서를 검토하고 결과를 안내할 예정입니다."
- 한 문장에는 생각 하나를 담습니다. 문장이 길어지면 둘로 나눕니다.
  - 예: "파일을 올린 뒤 검사를 실행하며 문제가 없으면 저장하고 문제가 있으면 오류를 표시합니다." → "파일을 올린 뒤 검사를 실행합니다. 문제가 없으면 저장하고, 문제가 있으면 오류를 표시합니다."
- 말로 해도 자연스러운 존댓말을 씁니다. 대화 답변은 '~요'로, PR, 이슈, 문서처럼 남는 글은 '~습니다'로 쓰고, 한 글 안에서는 하나로 맞춥니다. 보고서와 명세서는 장르에 맞으면 개조식을 씁니다.
  - 예(일상 대화): "실측했습니다." → "직접 재 봤어요."
  - 예(협업 문서): "두 가지, 즉 X와 Y" → "X와 Y 두 가지입니다."
  - 유지(전문 보고서의 용어): "실측 지연 시간은 120ms입니다."
- 활용이 맞는지 확인합니다.
  - 예: "검증을 거칠습니다." → "검증을 거칩니다."
  - 유지: "표면이 거칠습니다."
- 독자가 판단에 쓰는 정보만 남깁니다. 독자가 묻지 않은 측정 공백, 이미 아는 책임 주체, 기간 괄호는 판단에 영향이 없을 때 지웁니다.
  - 예(최종 결정을 누가 내리는지 독자도 이미 알고 있고 현재 판단에 영향을 주지 않는 경우): "기준은 A팀 제안값이며, 실제 기준값은 B팀이 정합니다." → "기준은 A팀이 제안한 값입니다."
  - 유지(결정 주체가 중요한 경우): "최종 기준은 B팀이 정합니다. B팀의 결정을 받은 뒤 적용할 예정입니다."
- 약속이나 작업 상태는 실제로 한 행동의 동사로 씁니다.
  - 예(코드 수정을 마쳤지만 테스트는 실행하지 않은 경우): "처리 완료" → "코드 수정은 마쳤습니다. 테스트는 아직 실행하지 않았습니다."

<a id="required-prose-notation"></a>
## 5. 표기

- 절과 절은 조사, 쉼표, "및"으로 잇습니다. 긴 대시(—)와 절 기호(§)는 인용, 코드, 공식 표기에만 씁니다.
  - 예(실행 순서 설명): "권한 확인 — 파일 열기" → "권한을 확인한 뒤 파일을 엽니다."
  - 유지(정확한 인용이나 공식 조항 표기): `§ 4.2`
- 가운뎃점(·)은 공식 명칭과 굳은 복합어에 씁니다.
  - 예: "가입·결제 성공 여부 확인" → "가입과 결제가 성공했는지 확인합니다."
- 제목과 목록 번호는 ASCII로 씁니다. 사용자가 정한 형식과 보호된 라벨, 문서 규격이 우선합니다.
  - 예: "① 설치" → "1. 설치"
- "핵심", "주요"처럼 강조하는 말은 근거를 함께 쓸 때만 씁니다.
  - 예(실제로 파일 처리 시간이 절반으로 줄어든 경우): "효율적인 처리 방식입니다." → "파일 처리 시간이 절반으로 줄었습니다."

<a id="contextual-patterns"></a>
## 6. 문맥으로 판단합니다

특정 표현이 나왔다는 사실만으로 고치지 않습니다. "하지만", "다만", "할 수 있습니다"가 실제 대조, 조건, 능력을 나타내면 그대로 둡니다. 표현을 바꾼 뒤에는 원래의 주체, 근거, 확실성, 독자에게 필요한 정보가 남았는지 확인합니다. 단어를 일괄 치환하거나 짧은 단정문을 반복하지 않고, 원문의 격식과 개성, 유머를 살립니다.

유지 예시:

- 실제 대조: "설치는 간단해요. 다만 운영 환경에서는 별도의 권한이 필요해요."
- 실제 능력: "이 도구는 네트워크 연결 없이도 실행할 수 있습니다."
- 필수 권한 경계: "비밀번호는 채팅에 입력하지 마세요." (안전한 입력 경로가 있으면 함께 안내합니다.)
- 장르에 맞는 간결함: 보고서의 상태 열에 적힌 "검증 대기", "승인 필요".

이 문장들은 의미와 형식에 필요한 역할을 하므로 표현만 보고 일괄 교정할 대상이 아닙니다.

## 7. 다 쓴 뒤 확인할 것

보고, 채팅, 슬라이드, 내레이션, HTML 문구를 다 쓰면 다음을 확인합니다.

1. 첫 문장이 결론이나 확인한 사실인가요?
2. 문장마다 누가 무엇을 하는지 드러나나요?
3. 같은 범위를 부정문으로 한 번 더 말한 문장이 있나요? 있으면 지웁니다.
4. 굵은 머리말 뒤에 같은 말을 되풀이했나요? 예: "**개인정보 검사.** 계정, IP, 경로 문자열이 0개인지 검사합니다." → "계정, IP, 경로 문자열이 하나도 남지 않았는지 확인합니다."
5. "~를 봅니다", "이제", "이를 통해", "하는 식으로", "라기보다" 같은 말이 문단마다 반복되나요?
6. 원문에 없는 대조("A가 아니라 B")나 근거 없는 낙관, 과장된 수식어를 넣었나요?
7. 계획을 완료한 일처럼 쓰지 않았나요?

이 목록은 검토할 후보를 찾는 용도입니다. 해당 표현이 문맥에서 제 역할을 하면 그대로 둡니다. 수정한 문장을 다시 읽어 새로 생긴 어색한 표현과 의미 보존을 확인합니다. 파일 원고의 정적 검사는 호출 스킬의 저작 검사 지침을 따릅니다. 별도 보고서나 검사 파일은 만들지 않고, 하지 않은 검사를 했다고 보고하지 않습니다.
