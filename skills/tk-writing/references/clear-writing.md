# 명확한 글쓰기

이 기준은 사람이 읽는 설명과 문서, 채팅 문구에 적용합니다. 호출한 스킬의 목적·출력 형식·승인 범위가 우선합니다. 글을 고친다는 이유로 새로운 사실이나 실행 권한을 만들지 않습니다. 원문에 문제가 없다면 그대로 둡니다.

<a id="hard-invariants"></a>
## 의미와 책임을 보존합니다

<a id="meaning-before-polish"></a>
### 표현보다 의미가 우선입니다

- **사실:** 원문이나 확인된 근거에 없는 사건, 원인, 수치, 예시, 인용, 근거, 약속을 더하지 않습니다. 중요한 논점과 배경은 짧게 쓰려고 삭제하지 않습니다.
- **행동과 책임:** 누가 무엇을 했고, 무엇을 할 예정인지, 누가 결정하고 승인하는지 구분합니다. 모르는 주체를 추측하지 않습니다. 추상적인 상태나 명사 나열 때문에 행동이 가려지면 실제로 확인된 동사를 사용합니다.
- **시간과 양태:** 완료·진행·예정, 능력·허가·의무·권고, 관찰·추정·가능성을 구별합니다. 유보 표현을 줄인다는 이유로 사실을 확정하거나 권고를 의무로 바꾸지 않습니다.
- **강도와 관계:** 긍정·부정의 강도, 비교의 순위와 범위, 동시·배타·인과·조건 관계를 보존합니다. 인접한 문장 사이에 없는 대조나 인과를 만들지 않습니다.
- **근거:** 날짜·수량·단위·기간·분모, 링크·인용·표·그림의 참조 대상을 유지합니다. 근거를 옮길 때도 원래 뒷받침하던 주장과 함께 옮깁니다. 독자가 따라갈 수 없는 내부 번호(댓글 ID, 문서 번호, 티켓 키)는 링크로 걸거나 무엇인지 풀어 쓰고, 둘 다 못 하면 뺍니다.
- **보호 대상:** 코드, API, JSON/YAML, 명령, 식별자, URL, 로그, 정확한 인용, 사용자 고정 문구와 공식 명칭은 임의로 바꾸지 않습니다. 코드 주석과 커밋 메시지는 저장소 관례를 따릅니다.

사용자가 글의 독자와 전달 상황을 알려 주었다면 이를 우선합니다. 독립적으로 읽는 문서에는 이해에 필요한 배경을 남기고, 이미 해당 정보를 공유한 대화에서는 반복을 줄입니다. 그 맥락을 확인할 수 없다면 지어내지 않습니다. 스타일 견본에서는 문장 리듬과 어조만 참고하며, 견본 속 사실을 끌어오지 않습니다.

## 독자가 바로 이해하도록 씁니다

- 결론이나 실제 결과를 먼저 말하고, 필요한 이유·근거·제약을 이어서 설명합니다. 내용을 예고하는 서론, 같은 말을 반복하는 요약과 공허한 결론은 줄입니다.
- 읽는 사람을 평가하거나 의례적으로 칭찬하지 않습니다. 습관적인 맞장구와 반박, 억지로 만든 ‘A가 아니라 B’ 구문, 근거 없는 낙관과 과장된 수식어를 피합니다. 실제로 중요한 반론과 제한 조건은 분명하게 전달합니다.
- 의미를 숨기는 추상어, 불필요한 명사화, 모호한 수동 표현을 고칩니다. 수동태나 전문어 자체를 금지하지 않으며, 도메인에서 정착된 표현은 유지합니다.
- 특정 단어를 일괄 치환하거나 짧은 단정문만 반복하지 않습니다. 원문의 격식·개성·유머를 존중하며, 요청된 어조만 필요한 만큼 바꿉니다.
- 제목과 라벨은 내용을 드러냅니다. 가능한 경우 ‘먼저 볼 것’ 같은 안내용 제목보다 ‘승인 전 확인 사항’처럼 구체적인 제목을 사용합니다.

<a id="korean-sentence-clarity"></a>
### 한국어 문장을 자연스럽게 씁니다

- 독자가 관계를 알아볼 수 있도록 필요한 조사·어미·주어·서술어를 사용합니다. 한국어에서 자연스럽게 생략하는 성분까지 억지로 반복하지 않습니다.
- 일상적인 대화에서는 말로 해도 자연스러운 존댓말을 씁니다. 필요하지 않은 한자어·격식·번역투를 덧붙이지 않습니다. 보고서와 명세서에서 관례적으로 쓰는 개조식은 장르에 맞으면 유지합니다.
- 문장 성분이 어색하게 결합하거나 잘못 활용된 부분을 확인합니다. 예를 들어 ‘검증을 거칠습니다’는 ‘검증을 거칩니다’로 고치되 ‘표면이 거칠습니다’는 그대로 둡니다.
- 사용자에게 약속하거나 작업 상태를 보고할 때는 실제 행동을 드러내는 동사로 표현합니다. 없던 승인 약속이나 완료 사실을 만들어서는 안 됩니다.

<a id="required-prose-notation"></a>
### 산문 표기

- 일반 설명문에서 긴 대시(—)와 절 기호(§)를 장식적으로 쓰지 않습니다. 정확한 인용·코드·공식 표기는 보존합니다.
- 한국어에서 가운뎃점(·)으로 관련 없는 명사를 계속 이어 쓰지 않습니다. 실제 관계에 맞게 조사, 쉼표, ‘및’을 사용합니다. 공식 명칭과 정착된 복합어는 유지합니다.
- 제목·목록의 새 번호에는 일반적인 ASCII 표기를 사용합니다. 보호된 라벨, 문서 규격과 사용자 지정 형식이 우선합니다.
- ‘핵심’, ‘주요’, ‘효율적인’처럼 근거 없는 강조는 내용에 맞춰 빼거나 실제 근거를 제시합니다. 확인되지 않은 예시를 만들어 채우지 않습니다.

<a id="contextual-patterns"></a>
## 어색한 표현을 판단하는 방법

표현이 나왔다는 사실만으로 잘못이라고 단정하지 않습니다. 문맥에서 기능이 없는 반복·억지 대비·형식적인 양보·상투적인 서론을 찾아 줄입니다. ‘하지만’, ‘다만’, ‘할 수 있습니다’는 실제 대조·조건·능력 표현이라면 유지합니다.

표현을 삭제하거나 바꾼 뒤에는 원래의 행동·책임·근거·확실성·독자에게 필요한 정보가 남았는지 확인합니다. 새로 생긴 어색한 표현도 확인합니다. 길이나 문장 수로 점수를 매기지 않고 의미가 보존되었는지 판단합니다. 이미 자연스러운 글은 억지로 수정하지 않습니다.

<a id="authored-copy-pattern-check"></a>
## 최종 문구 점검

보고·채팅·슬라이드·내레이션·HTML 문구에서도 같은 기준을 적용합니다. ‘핵심은’, ‘라기보다’, ‘이제’, ‘이를 통해’, ‘하는 식으로’ 등의 반복, 근거 없는 결론, 계획을 완료한 것처럼 말한 부분을 문맥에서 확인합니다. 패턴 일치는 검토 후보일 뿐입니다.

수정한 문장을 다시 읽고 사실과 실행 상태, 조건, 어조, 조사·어미를 확인합니다. 별도 보고서나 검사 파일은 요구하지 않습니다. 파일 원고의 정적 검사는 호출 스킬의 저작 검사 지침을 따르며, 검사를 수행하지 않았다면 실행했다고 보고하지 않습니다.
