# 설명 렌더러 계약

<a id="route-by-selected-form"></a>
## 선택한 형식에 따른 분기

`tk-explain`과 `tk-research`의 요청된 HTML은 파일 확장자가 아니라 결론을 설명하는 데 필요한 내용의 형태로 선택합니다.
사용자가 지정한 형식이나 기법의 고유 형식이 우선하며, 미지정일 때는 다음 기본값을 적용합니다.

- 한국어 `tk-explain` 설명 페이지는 일반 HTML 셸을 기본으로 사용합니다. 결론·핵심 이미지·짧은 부연 뒤에 접이식 근거를 두며, 여러 팀 논의 문서는 담당 스킬의 한 줄기 문서 순서를 따릅니다. 관계나 흐름이 언급되었다는 이유만으로 패널 보드로 바꾸지 않습니다.
- 구조 도해 자체가 설명의 중심일 때만 archify 보드를 선택합니다. `tk-research`에서는 구성요소의 연결, 호출, 상태 전이, 데이터 흐름이나 시간 순서를 보여 주어야 결론을 설명할 수 있으면 기존 archify 기본값을 유지합니다. 단순히 항목에 순서가 있다는 이유만으로 도해를 만들지 않습니다.
- 비교표, 체크리스트, 할 일, 단순 절차, 권고 목록이나 근거 사진이 중심이면 일반 HTML을 기본으로 사용합니다. 도해가 결론에 필요하지 않으면 이름 붙은 기법을 강제하지 않습니다.

일반 문서형 HTML은 [HTML 출력](html-output.md), [문서 조립](html-assembly.md)과 [독자용 표현](html-reader.md)에 따라
현재 설치된 `tk-writing`의 공통 셸과 도우미를 사용합니다. 기법의 고유 구조가 필요한 HTML은 아래 공통 계약으로
독립 작성할 수 있습니다. 두 경로 모두 정식 선택지이며 archify 설치 실패의 대체 경로가 아닙니다.
선택한 archify에는 여전히 의존성과 finalize가 필요하고, 실패하면 해당 분기를 차단합니다. 다른 형식으로 말없이 바꾸지 않습니다.

### 제작 전 형식 제안

HTML의 구체적인 표현 형식이 미지정이고 선택을 위임받지 않았으면 제작 전에 추천 하나와 성격이 다른 대안 1~2개를
각각 한 줄 이유와 함께 한 번 제안하고 선택을 받습니다. `표 중심 문서`, `흐름도 중심 보드`처럼 독자가 볼 형태로 설명하며,
내부 스키마나 다이어그램 세부 문법을 고르게 하지 않습니다. 근거와 요청에 맞는 대안만 제시하고, 선택지가 하나뿐이면
그 이유를 알리며 부적합한 대안을 채우지 않습니다. `HTML로`만 요청한 것은 표현 선택 위임이 아닙니다.
이미 선택한 형식은 다시 묻지 않으며 `알아서`, `추천대로`처럼 위임받았으면 내용에 맞춰 바로 제작하고 선택한 형식과 이유를
완료 보고에 적습니다. HTML을 요청하지 않은 일반 대화에는 이 제안이나 파일 제작을 추가하지 않습니다.

## 공통 단일 HTML 계약

모든 페이지는 인라인 CSS/JS와 내장 자산을 포함하는 하나의 오프라인 HTML이며, 시작하거나
상호작용할 때 외부 요청을 보내지 않습니다. 클릭할 수 있는 출처 URL은 참조이며 가져오는 리소스가 아닙니다. 의미 있는
`<title>`, 문서 언어, 의미론적 제목, 접근 가능한 이름, 눈에 보이는 키보드
포커스, 밝은·어두운 테마 토큰과 동작 줄이기 처리를 포함합니다. 작성한 기법 페이지는 사용자의 언어와 HTML 테마
선호를 따릅니다. 전달용 studio의 테마는 아래 공통 후처리 계약을 따릅니다.
후처리한 studio 파일은 같은 폴더나 하위 폴더의 로컬 영상을 상대 경로로 참조할 수 있습니다. 외부 네트워크 리소스 예외가 아닙니다. 영상은 기존 이미지 자리에 두고 이미지를 poster·인쇄·내보내기·no-JS·파일 없음 때의 대체 그림으로 보존합니다.
대체할 이미지 없이 영상을 삽입하면 별도 미리보기 이미지를 `poster`로 지정합니다. 미리보기 장면을
바꾸려고 `src`에 media fragment(`#t=`)를 붙이거나 초기 seek를 수행하지
않습니다. `#t=`는 실제 재생 시작 위치도 옮겨 첫 내레이션·자막을 건너뛸 수 있습니다. 설명 영상은
항상 0초에서 시작하고 autoplay·자동 mute를 추가하지 않으며 사용자의 재생 행동으로 소리와 함께
시작합니다. poster와 재생 시작점은 별개이며 첫 내레이션·자막과 재생 전 이미지를 각각 확인합니다.
핵심 사실과 모든 단계는 JavaScript 없이도 읽을 수 있어야 합니다. 답변을 펼쳐 보여 줄 때는 기본 `<details><summary>`를
사용합니다. 인라인 JS로 포커스·스크롤 강조를 향상할 수 있지만 필수 콘텐츠의 유일한 사본을
숨길 수는 없습니다. 인라인 SVG에는 의미 있는 레이블과 올바른 기하 구조가 필요합니다. `tk-explain`의 코드 블록은 사용자가 요청한 경우에만 넣습니다. 코드 발췌는
고정한 head 바이트에서 그대로 복사하고 `path:line @ sha`를 표시합니다. base·diff 스냅샷은 별도로 구분하여 표시합니다.

모든 렌더러와 변형에 동일한 실행의 `evidence.md`, 담당자의 작성자 점검, 출처 연결과 해당되는
독립 정확성 검토를 사용합니다. `tk-explain`은 자체 `scripts/visible_text.py`로 텍스트를 추출하며,
`tk-research`는 보고서의 주장, 출처와 포함 범위를 대조합니다. 최종 바이트를 정적으로 검사하여
HTML/CSS/JS에 외부 URL·리소스 로드가 있는지, `<title>`이 비어 있지 않은지, 비어 있지 않은
`<summary>`가 각 `<details>`의 첫 자식인지 확인합니다. no-JS 읽기 경로와 출처 발췌를 검증합니다.
후보 식별 정보와 점검 결과를 실행 근거에 기록합니다. 정적 검사는 브라우저 근거가 아닙니다.
공통 셸의 `[data-ht-download]`를 제공하는 페이지는 최종 후처리 뒤 [다운로드와 파일 공유](html-output.md#download-and-file-sharing)의
`package_html.py --check`로 payload·manifest와 최종 허용 목록 바이트를 검사합니다. 검사 실패는 전달 실패입니다.
이 셸 다운로드 기능이 없는 archify·독립 HTML에는 `template[data-ht-export]`를 강제하지 않습니다.
요청한 상호작용 점검은 여전히 `tk-browser-verify`로 전달합니다. 선택한 archify 페이지만 추가로
`finalize`를 실행합니다. 독립적으로 작성한 HTML에는 archify 설치나 receipt가 필요하지 않습니다.

## 모든 전달 HTML의 공통 후처리

사람에게 전달하는 모든 tk-* HTML은 원본의 생성·검증이 끝난 뒤 현재 설치된 `tk-writing`의
[피드백 studio](feedback-studio.md)를 적용하여 전달 폴더에는 피드백 주입본 `<stem>.html` 한 벌만 두고
이를 열람본으로 안내합니다. 검증한 원본과 해당 receipt는 `.tigerkit/evidence/<skill>/<run-id>/`에
바이트를 바꾸지 않고 보존합니다. 기법별 HTML도 같은 규칙을 따릅니다. 설명·조사·갤러리·QA 시트·prototype·시각 질문에 같은 계약을 적용합니다.
영상 피드백 플레이어는 같은 공통 테마·항목 수정 자원을 사용하는 자체 목록을 유지하며 studio를
중복 주입하지 않습니다. 캡처 전용 임시 HTML은 전달물이 아니므로 후처리를 생략합니다.
완료 보고에는 원본의 실제 검사와 `전달본: 피드백 주입본(실제 통과한 검사)`을
구분합니다. archify 원본에만 `finalize 통과본`이라고 쓰며, 일반 HTML에 finalize receipt를 요구하거나 주입본을 원본의 finalize 통과 바이트로 보고하지 않습니다.
후처리한 최종 바이트에도 정적·해당 상호작용 검사를 적용합니다. 후처리에 실패하면 근거 폴더의 원본을 보존하고 실패 사유를 알립니다. 전달 폴더에 기존 유효본이
있으면 유지합니다. 원본만 전달하는 예외를 택하면 그 한 벌만 `<stem>.html`로 복사하고 누락 기능을 알립니다. 이 공통 단계는 렌더러를 바꾸거나 HTML 제작을 새로 요구하지 않습니다.

## 전달 HTML의 고정 테마

공통 셸, 피드백 UI와 영상 피드백 플레이어의 색·글꼴 스택·모서리는
[HTML 출력의 고정 토큰](html-output.md#frozen-delivery-theme)을 사용합니다.
archify 3.2.0을 기준으로 TigerKit 안에 값을 고정하며 후속 변경을 자동 추종하거나 동기화 점검을 만들지 않습니다.

## 선택한 archify 분기

의존성은 `archify >= 3.2.0`(stable SemVer)이며, 출처는 `tt-a1i/archify`입니다.
검증한 upstream은 `d6059331abbddb49bca380ff46dca8ce33158b04`이며 버전은 `3.2.0`입니다.
호스트에 설치된 스킬 위치를 사용하고 그곳의 `skill-release.json`과 `SKILL.md`를 읽습니다.
폴더 이름에서 추론하지 말고 `skillId`, 저장소 식별 정보와 버전을 검증합니다.
알 수 없거나 비교할 수 없는 메타데이터는 통과가 아닙니다. 의존성이 없거나 오래되었으면 `Blocked`를
설치된 버전·필수 버전 및 `tk-wizard` 설치·업데이트 인계와 함께 반환합니다. archify를 설치하거나,
업데이트하거나, vendoring하지 않습니다. 선택한 archify 설명 페이지와 조사 페이지는 상호작용을 요청한 경우를 포함하여 TigerKit의
기존 문서 빌더·보고서 템플릿으로 절대 대체하지 않습니다.

초안을 작성하기 전에 설치된 `references/explainer-authoring.md`를 읽습니다. 모든 작업은
호출 담당자의 `.tigerkit/tmp/<skill>/<run-id>/` 안에서 수행합니다. 고유한 패널·블록 ID와 같은 디렉터리의 이미지·spec
파일을 사용합니다. 구현이나 캐시된 예시를 복사하지 말고 설치된 구문을 따릅니다.
다음을 실행합니다.

```sh
node <archify>/bin/archify.mjs finalize explainer candidate.archify.md <final.html> --json
```

commit된 코드 발췌와 검증한 저장소 참조에는 `--repo-root <repo>`를 사용합니다.
`@code` 출처는 고정한 commit·경로·행에 존재해야 합니다. worktree 바이트나
base 행을 head 발췌로 제시하지 않습니다. 하나의 문서가 여러 스냅샷을 다루면 버전을 명시한 출처와 원문 그대로의 diff·코드 블록을
사용합니다. 저장소 메타데이터에 일치하는 revision을 추가합니다.
Explainer 3.2.0의 finalize는 validate/deliver/check를 실행하며 브라우저 관문은 아닙니다. receipt를 저장합니다.
완료는 이번 명령의 exit가 0이고 이번 stdout JSON의 `ok`가 `true`일 때만 판정합니다.
그 결과의 `artifact.path`와 `artifact.sha256`을 실제 원본 HTML 경로·SHA-256과 대조합니다.
실행마다 새 결과 경로를 사용하며, 남아 있는 이전 요약·receipt·HTML의 존재만으로 성공을 판정하지 않습니다.
실패하거나 해시가 다르면 전달을 멈춥니다. 기본 `validate` 통과는 finalize의 기본 `showcase` 품질
통과를 뜻하지 않습니다. 설치본의 지원 옵션을 확인해 같은 품질로 사전 검사하고, strict 배치 진단의
대상과 수정 힌트를 사용합니다. 무작위 배치 조합을 반복하거나 진단을 피하려고 품질 기준을 낮추지 않습니다.
finalize만으로 브라우저 실행을 주장하지 않습니다. 수정한 뒤에는 다시 생성합니다.
이미지를 포함한 단일 파일·오프라인 출력을 확인하고, 출처 URL은 참조로만 유지합니다.

중복 업데이트 점검을 실행하지 말고 finalize의 업데이트 receipt를 사용합니다. 업데이트
안내가 필요하면 한 번만 보여 줍니다. 사용자의 검증된 일괄 업데이트 절차를 알고 있다면 이를 우선합니다.
업데이트를 절대로 실행하지 않습니다. 버전이 충분히 새롭다고 해서 생성된 출력이 통과했다는 증거는 아닙니다.
archify 원본의 테마와 receipt는 변경하지 않습니다. studio는 원래 archify 테마 버튼을 그대로 쓰며
[공통 후처리](feedback-studio.md)에 따라 독자 선택과 저장 키를 연결합니다.
생성 기본값은 [HTML 출력](html-output.md)의 `html.theme` 계약을 따릅니다.

명시적 요청이나 추천 선택에 따라 상호작용을 제공하면 [상호작용 예시](interactive-examples.md)를 읽습니다. 기본
다이어그램 선택, 안내 단계, 포커스와 경로 탐색은 archify 안에서 작동하는 상태로 유지합니다.
이미지로 평면화하지 않습니다. 이미지 변환은 기본
다이어그램 문법으로 표현할 수 없는 공간 그림에 사용하며, [장면 그림](scene-figures.md)을 따릅니다.

소프트웨어가 아닌 주제에서는 설치된 스키마를 사용하여 기본 `@diagram`과 의미 있는 `meta.legend`
항목(또는 지원되는 명시적 숨김 범례)으로 시작합니다. 축약된
소프트웨어 기본값은 잘못된 범주를 가르칠 수 있습니다. 그러한 오류가 발생하기를 기다리지 말고
사용자 정의 레이블을 선택합니다. 모든 노드 레이블을 검증합니다. ID는 설명용 레이블이 아닙니다.
한국어 설명 페이지에서는 중국어 레인 라벨이 남을 수 있는 `@workflow` 대신 `@architecture`와
명시적인 한국어 노드·연결·범례를 사용합니다. 순서와 분기 의미를 보존하고 설치된 작성 문법에서
확인한 레이블만 사용합니다. 노드 레이블만 고쳐 범례도 바뀌었다고 간주하지 않습니다.

알려진 3.2.0 제한은 다음과 같습니다. explainer chrome은 중국어 이외의 언어에서 영어로 대체됩니다. 축약된 workflow
