# 여러 저장소를 처리할 때 초기화 중복과 자원 경합을 제한합니다

사용자는 여러 저장소의 작업을 병렬로 실행하면서 의존성 설치가 중복되어 자원이 부족해진 사례를 보고했습니다. 기준 `1b80b051`의 `tk-pr-sweep/references/execution.md`에는 중첩 `SDD`의 순차 실행만 있었고 다른 코드 수정 항목의 초기화 부하를 제한하지 않았습니다. 당시 실행 기록과 실제 자원 사용량은 이번 작업에서 재현하지 않았습니다.

## 상류 확인과 판단

고정한 상류는 `stablyai/orca@c3d3df497f950334a00d3e2d47fc6227983873a3`입니다.

- 문서: `docs/site/content/docs/model/orca-yaml.mdx`, `docs/automated-setup-tab-design.md`.
- 구현: `src/shared/orca-yaml-hook-types.ts`, `src/main/runtime/runtime-repository-hooks-commands.ts`.
- 관련 검증: `src/main/hooks-orca-yaml-parsing.test.ts`, `src/main/hooks-effective-hook-resolution.test.ts`. 코드는 읽었으나 상류 테스트는 실행하지 않았습니다.

`adapt`: 유효한 저장소 생성·파괴 스크립트를 기존 호스트 수명주기에서 활용합니다. 생성 설정과 로컬 정책의 실제 선택을 확인하고, 성공한 초기화는 자식에게 넘겨 중복 설치를 생략합니다. 스크립트의 존재와 저렴한 실행 비용을 구분하며, 비동기 생성 응답은 초기화 완료로 취급하지 않습니다.

`keep`: 새 작업공간의 정확한 머리와 소유권, 설정·스크립트의 기존 실행 권한, 정리 권한, 공유 의존성 보호를 유지합니다. 설정이 없으면 저장소 전체에 걸쳐 코드·`Git` 변경 항목을 한 건씩 준비·실행·검증합니다. 이미 가볍다고 확인한 생성 스크립트도 실제 테스트·서버 부하가 크면 순차 실행합니다.

`omit`: `Orca` 설정 복제, 설치·자동 실행, 운영체제별 명령, 전역 일정 관리자, 잠금과 용량 기록은 추가하지 않습니다. 순서는 기존 대기열과 자식 인계에서 처리합니다. 가벼운 읽기·답변 전용 항목의 안전한 동시 실행도 유지합니다.

## 소유와 검증

자원 한도와 작업공간 준비 인계는 `tk-pr-sweep`이 소유하며, `Orca` 세부 조사는 설치되어 있고 작업공간이 필요한 분기에서만 읽습니다. `tk-pr-respond`에는 부모가 준비한 초기화를 재실행하지 않고 새 무거운 작업을 부모와 조정하라는 경계만 추가합니다.

생성 스크립트 재사용, 스크립트 없는 여러 저장소의 단일 항목 실행, 무거운 스크립트, 실제 설정 선택, 비동기 완료, 파괴 실패, 무거운 테스트, 자식의 중복 설치를 다루는 평가 8건을 추가했습니다. 새 컨텍스트에서 모델을 실행하거나 실제 `Orca` 작업공간을 생성한 결과가 아니라 실행 가능한 평가 명세입니다. 실행 코드 변경이 없으므로 별도 문자열 검사 단위 테스트는 만들지 않습니다.

상시 추가 문구는 생성 전 자원 한도 결정, 부모에서 자식으로의 초기화 소유권 전달, 설치 외 검사 부하 제한을 각각 담당합니다. 이를 빼면 병렬 생성이 먼저 설치를 시작하거나 자식이 초기화를 반복할 수 있습니다. 세부 설정은 조건부 참조에 두었습니다.
