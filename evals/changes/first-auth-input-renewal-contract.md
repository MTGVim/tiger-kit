# 첫 인증 입력의 갱신 계약 확정

제공된 회고와 기준 `bbef7882`의 문서를 대조했습니다. `environment.md`의 조사는 재요청에만 명시되어 있었고, 첫 양식은 단일 토큰 예시만 제공했습니다. 원래 앱과 새 컨텍스트의 실행은 재현하지 않았으므로 당시 모델의 판단 원인은 가설로 남깁니다.

## 근거와 적용 범위

- 고정된 상류 근거: [RFC 6749, 2012-10, 1.5절과 6절](https://www.rfc-editor.org/rfc/rfc6749). 발급 여부는 선택 사항이지만 해당 갱신 방식에서는 갱신 토큰이 필요합니다. 이 구분을 첫 입력 조사 순서에 적용합니다. 표준의 전송 형식을 앱에 강제하지 않고 실제 앱 클라이언트의 계약을 따릅니다.
- `adapt`: 첫 입력 요청 전에 부트스트랩과 지원 갱신 경로를 함께 조사하고, 그 경로가 사용자 입력을 요구하면 최초 필수 필드에 포함합니다. `tk-browser-verify`가 조사와 양식을 소유합니다.
- `keep`: 갱신 경로가 없거나 기존 브라우저 상태로 갱신할 수 있으면 별도 갱신 입력을 요구하지 않습니다. 비밀 비노출, 사용자 입력 보존, 권한 검사, 단일 갱신 담당자와 회전 처리도 유지합니다.
- `omit`: 일반 인증 보존 참조와 생성기를 일괄 수정하거나 새로운 인증 도구·상시 갱신기를 만들지 않습니다. 공통 참조의 `optional`은 모든 앱이 갱신 토큰을 제공한다는 보장이 없음을 뜻하며, 구체적인 입력 계약은 검증 스킬이 소유합니다.
- 준비 계획과 필요한 `Seed`에는 필드명과 갱신 경로 유무만 남깁니다. 비밀 값이나 새 상태 문서는 추가하지 않습니다.

## 검증 범위

첫 입력에 갱신 토큰이 필요한 앱, 갱신 경로가 없는 앱, 브라우저가 갱신 상태를 관리하는 앱, 준비 계획의 필드 누락을 다루는 평가 4건을 추가했습니다. 이는 실행할 평가 명세이며 새 컨텍스트에서의 모델 실행 결과가 아닙니다. 정적 릴리즈 검사는 별도로 수행합니다.

상시 문구를 검토하면 첫 조사 순서는 재요청 전용 해석을, 갱신 필드의 필수 지정은 선택 입력 해석을, 양식의 두 분기는 단일 필드 예시 편향과 과잉 수집을, 계획 기록은 인계 시 계약 누락을 각각 방지합니다. 비밀 저장 계약은 기존 참조를 재사용합니다.
