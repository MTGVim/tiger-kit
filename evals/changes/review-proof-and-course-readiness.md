## 실제 변경과 경계

코스의 선택적 `readiness` 데이터는 관련 목표, 출처 근거와 확실성, 구체 문항, 모든 선택지의 이유,
오프라인 복습 설명을 포함합니다. 추정 항목은 홈에도 확인 필요로 표시합니다. 소비자는 정답·오답·미응답
피드백과 재시도를 사용할 수 있으며, JavaScript 없이도 설명과 복습을 읽을 수 있습니다.
기존 질문 컴포넌트를 함께 사용하고 학습 진도 형식·완료 조건·TTS 선택을 변경하지 않습니다.
응답은 저장·전송·진도 내보내기에 들어가지 않습니다. `readiness` 변경은 코스 `revision`을 요구하고 갱신일을
바꾸되 레슨 `fingerprint`와 수동 진도는 유지합니다. 선수지식의 실제 타당성은 구조 검증기가 증명하지 않습니다.

tk-teach의 학습 기록은 계속 실제 관찰에 한정됩니다. 재개 시 이미 입증한 답변을 다시 진단하지 않고,
미응답과 실제 오답, 선언한 경험과 입증한 이해를 구별합니다. 전달 시에도 근거와 불확실성만 승인 범위에서 보존합니다.

## 검증과 지시문 부하

`readiness`의 선택적 생성, 잘못된 데이터 거절, 추정 표시, `revision`·날짜·레슨 보존 테스트는
기준 코드에서 실패했고 후보에서는 통과했습니다. 실제 `player.js`의 응답 처리 함수를 VM에서 실행하여
미응답·오답별 해설·정답 재시도와 저장/네트워크 호출 부재를 검사했습니다. 이는 DOM 대역을 사용한
JavaScript 검증이며 실제 브라우저·접근성·화면 검증으로 취급하지 않습니다.

실제 `file://` 번들 및 독립 레슨에서 `390/1280px`, `light`/`dark`/`system`의 12개 조합과 JavaScript
미사용 경로를 `headless` `Chromium` 153에서 실행했습니다. `Enter`로 선택적 진단을 펼치고 방향키로
응답을 바꾸며 미응답·오답·정답·재시도, `localStorage` 비변경, 빈 완료 목록과 `readiness` 없는
`progress` 내보내기, 외부 HTTP 요청 부재를 확인했습니다. 기본 다운로드는 실패했으므로 구현
담당 단계에서 `npm`의 `Chromium` 바이너리와 `Noto Sans KR`을 작업 전용 임시 경로에 준비했습니다.
소비자 산출물이나 호스트의 지속 설정에는 의존성을 추가하지 않았습니다.
첫 실행의 닫힌 내보내기 영역, 두 번째 실행의 닫힌 `no-JS` 복습 영역에서 테스트 탐색이
실패했습니다. 실제 사용자처럼 `details`를 펼치도록 테스트만 고쳤으며 실패 로그를 보존했습니다.

동일한 코스 원본 JSON을 기준·후보 빌더에 주어 `390/1280px`의 `light`/`dark` 화면을 캡처했습니다.
코스 홈의 `hero` 영역은 네 조합 모두 바이트가 동일했으며, 별도의 일반 `viewport` 캡처에서
선택적 문항과 오답별 해설·복습의 줄바꿈·모바일 너비·색 대비를 직접 확인했습니다.
기존 빌더는 지정한 JSON과 그 미디어만 읽으므로 주변 `ignored` 실행 파일은 빌드 입력이 아닙니다.
브라우저·`context`·페이지는 실행 후 종료했고 사용자 세션·서버·클립보드는 사용하지 않았습니다.

최종 전체 검사에서 기존 훅 카드와 모바일 제목·출처의 여러 줄 경계 상자가 한국어 폰트에서
겹치는 문제가 드러났습니다. 기준 버전의 동일한 실제 브라우저 평가에서도 재현했습니다.
글자 크기에 따른 공통 줄 간격을 적용하고 각 범례·카드·다음 요소·출처·전체 높이를 같은
간격으로 계산하도록 수정했습니다. 글자 크기와 원자료·의미 있는 강조 대상은 유지합니다.
기존 겹침 검사를 완화하지 않았습니다. 같은 원본의 11개 슬라이드를 세 너비와 두 테마에서
실제로 검사했을 때 기준은 24개 조건에서 경계 상자가 겹쳤으며 후보의 66개 조건에서는
겹침·경계 이탈이 모두 없었습니다. 전체 원래 브라우저 평가도 다시 실행합니다.

리뷰 6개, 코스 5개, `teach` 3개의 행동 평가를 추가하여 회귀와 정당한 사양 변경, 동적 사용처,
간접 소비자, 부족한 근거, 이미 가르치는 개념, 불확실한 공백, 진단 생략, 재개와 미응답을 구별합니다.
14개 입력을 기준 지침과 후보 지침을 읽은 두 별도 모델 `context`에 주고 실제 응답을 비교했습니다.
예상 정답·상대 응답·회고는 전달하지 않았습니다. 양쪽 모두 회귀/승인 변경·불확실성·진단 생략과
기록 재사용을 구별했습니다. 기준의 선택지별 해설은 일반 설명에 머물렀고 후보는 각 선택지의
오개념을 구체화했습니다. 한 번씩 수행한 `batch`이므로 일반적인 성능 우위나 학습 효과를 증명하지 않습니다.

추가로 `evals/skills/tk-review/review-proof-fixtures.json`의 실제 코드·보호 테스트·별도 계약
`oracle`로 다섯 `fixture`를 만들고 `base`/`head`를 고정했습니다. 결과 수 축소, 예외 은폐, 간접 소비자
누락은 `head` 테스트가 GREEN이어도 독립 `oracle`에서 실패했고, 승인된 사양 변경은 `oracle`도 통과했습니다.
동적 플러그인 삭제는 실제 로딩과 기존 테스트가 실패했습니다. 별도 `unittest`가 이 구별을 재현합니다.
새로운 두 독립 모델 `context`는 `oracle`/정답을 보지 않고 `exact` `diff`와 사양·소비자·기존 테스트
출력을 검토했습니다. 기준·후보 모두 실제 결함 4개를 찾았고 승인 변경의 거짓 양성은 0개였습니다.
따라서 이 표본에서는 탐지 우위를 주장하지 않으며 최소 판단 품질을 유지한 증거로 사용합니다.
실제 추가 코드 작성·검증 프로세스는 양쪽 0회였고 기존 근거를 재사용했습니다. 읽기 도구 호출은
기준 5회(내부 Git 95회와 `cat` 1회), 후보 3회(내부 Git 56회와 `hash` 2회)였습니다.
출력 분할·재읽기 방식이 달라 토큰·시간 절감의 비교 지표로 사용하지 않습니다.

상시 문장 삭제 대조는 계약 수준에서 수행했습니다. 테스트 변경 대조를 빼면 GREEN이 이전 계약을
보호하는지 따질 조건이 사라지고, 동적 조회와 간접 소비자를 빼면 정적·단방향 증거로 부재/안전을
단정할 수 있습니다. 기존 `fresh-state` 원칙을 재사용하며, 중복이었던 `review-protocol`의 새 연결 문장은
제거했습니다. 두 학습 스킬의 짧은 조건부 포인터를 빼면 `untaught` 구별과 선택적 진단의 읽기 조건이
사라집니다. 상세 계약은 분기 참조로 내렸습니다. 실제 모델을 이용한 문장 삭제 실험은 하지 않았습니다.
